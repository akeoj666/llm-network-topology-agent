# D 量化评测表

> 本表所有数字由 `python tools/report_d.py` 现场重算，不是手抄。
> 只有最后一节「人工 PT 实测」是人工观察记录，其余全部可复现。

## 0 评测口径

| 指标 | 定义 | 怎么算的 |
|---|---|---|
| 断言通过 | 用例里声明的「应该通/不通」与实际推算是否一致 | `pktlab.accept` 重算 |
| 一致性检查 | 网关有效性、点对点同网段、ACL 兜底、VLAN 二层配套等 | `pktlab.accept._static_checks` |
| 连通性 | 主机对推算结果（通 / 不通） | 同上网段二层 + 跨网段找路 + ACL 首条命中 |
| 故障定位率 | 注入某类错后，校验器报出的码与预期一致的比例 | `pktlab.faults` 注入 + 校验 |
| 闭环收敛率 | 可修故障被修到「校验通过」的比例 | `pktlab.repair` 重跑 |
| 语义保持率 | 修完之后验收断言与一致性检查仍全过的比例 | 修完再过 `accept` |
| 容器完整性 | `.pkt` 解密再加密后与原文件字节一致 | `codec` 往返 |

**口径声明**：连通性是**模型推算**，不是 PT 实跑。PT 没有可脚本化仿真接口，
所以「断言通过率」反映的是「生成结果与需求意图一致」，不等于「PT 里真的 ping 通了」。
后者只有最后一节那 5 个用例有人工证据。

**「配置一次通过率」的口径**：一轮生成即通过 schema 校验与语义护栏，**且本地修复器一处都没动**（`本地修复 = 0`）。
只要回灌重试过、或任何一条修复器介入过，就算「非一次通过」——不能拿「修完能过」冒充「一次就对」。

> 只有 3 个用例留有带轮数的审计档，其余（包括 7 个 YAML 直读通道的课内实验）没有「模型第几轮」这个概念，表里标「—」且不计入分母。YAML 通道是构造输入、不是生成，算进来会把通过率人为抬高。
> 其中 2 个早期档没有「本地修复」字段。它们轮数为 1 且当轮校验错误数为 0，修复器没有入口可动，按 0 计——这是**推断**，不是留档，已在表里保留「—」以便区分。
> **样本这么少，这一栏不能当结论用，只能当观察。**

## 3 鲁棒性：故障注入闭环

| 指标 | 数值 | 说明 |
|---|---|---|
| 故障类型 | 24 类 | 覆盖编址/结构/VLAN/ACL/链路五类 |
| 定位准确率 | **24/24（100%）** | 报出的错误码与预期一致 |
| 闭环收敛率 | **22/22（100%）** | 可修故障全部修到校验通过 |
| 幂等率 | 22/22 | 再修一次不再产生改动 |
| 语义保持率 | **20/20（100%）** | 修完后C2验收仍全过 |
| 按设计不修 | 2 类 | 子网重叠、掩码非法——怎么挪没有唯一答案 |
| 排障平均轮数 | **1.00 轮**（22 条收敛样本，最多 1 轮） | 注入 1 个故障后「校验→修→再校验」的来回次数 |
| 一次修好率 | **22/22（100%）** | 轮数分布：1 轮 22 条 |

**「排障轮数」的口径**：轮数 = 修复器实际执行的 pass 次数。1 轮表示「扫一遍错 → 全部修好 → 复验通过」，不需要第二轮；上限 `max_pass = 5`，到顶未收敛即判失败（当前样本中没有到顶的）。

这些数字测的是**修复器**的收敛能力，不是模型的。模型那边对应的指标是上面的「配置一次通过率」——两者不能混起来说「AI 排障只要 1 轮」。

### 3.1 多故障叠加（轮数指标的区分度）

单点注入的轮数必然是 1——一个错修一遍就没了，这个数字说明不了任何问题。所以额外在同一基线上一次堆 k 个错，看修复器会不会被拖进第二轮：

| 叠加规模 | 组合数 | 收敛 | 平均轮数 |
|---|---|---|---|
| 一次注入 2 个错 | 76 | 76/76 | 1.00 |
| 一次注入 3 个错 | 189 | 189/189 | 1.00 |
| **合计** | **265** | **265/265（100%）** | **1.00** |

轮数分布：1 轮 265 条；最多 1 轮。

**这个结果说明什么、不说明什么**：265 组叠加故障全部在 1 轮内收敛，说明修复器是「一次扫描、规则全部并行应用」，不是「每轮只修一类、反复试」。代价是：**本实验没有观测到需要 2 轮以上的场景，所以「平均 1.00 轮」不能拿来证明修复器在高复杂度下仍然高效**——只能说在已覆盖的故障类型组合里没有被拖进第二轮。

## 7 已知缺口

诚实列出没测到的部分，避免把「没测」说成「通过」：

1. **没有全用例 PT 实测**。11 个用例只人工验了 5 个，其余是模型推算。
2. **没有统计意义上的泛化测试**。生成类用例只有 5 个样本，不够支撑「任意需求都能生成」的结论。
3. **没有对比基线**。没有「纯 LLM 直接写 pkt」或「手写」的对照组，所以这些绝对数字
   不能换算成「比人工快多少」，只能说明本系统自身的一致性。
4. **生成耗时只统计到部分用例**（有的历史产物没留审计档，表中标「—」）。
5. **没有并发/压力测试**。全部是单次串行调用。
6. **「配置一次通过率」只有 3 个样本**，且其中 2 个的「本地修复」
   是推断值而非留档值。3/3 这个数字不足以支撑「模型基本一次就对」，
   它只说明「在留档的这几次里，没有一个需要回灌重试」。
7. **「排障平均轮数」没有观测到多轮场景**。265 组叠加故障全部 1 轮收敛，
   所以这个指标目前只能证明「没有退化到反复试」，证明不了「复杂场景下也快」。
   真正会让它变大的场景（修复规则相互冲突、修 A 破坏 B）没有被覆盖到。
8. **故障目录是自建的**，24 类错误不代表真实世界里的错误分布——
   它测的是「我们想到的错能不能修」，不是「实际会遇到的错能不能修」。
