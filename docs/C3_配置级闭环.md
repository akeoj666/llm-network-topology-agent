# C3 配置级排障闭环

> 判定语：**教师/同学预置 1 个故障（错掩码、漏 network 等），Agent 在 ≤3 轮内自动定位并修复，全程日志可复现**。
> 部分给分：4–5 轮修好 → 1 分；未能自动修复 → 0 分。

---

## 1 这一项原来缺什么

之前项目里已经有 24 类故障注入和自动修复（`faults.py` / `repair.py`），
但那些都跑在 **DSL 层**——修的是「设计图纸写错了」。

C3 要的是另一件事：**给一份已经下发的 IOS 配置，找出哪里写错了并改对**。
两者的输入形态完全不同：

| | DSL 层（原有） | 配置级（C3 补的） |
|---|---|---|
| 输入 | YAML 字典 | `running-config` 文本 |
| 错误形态 | 结构错（缺字段、网关指错） | 文本错（掩码写错、少一条 `network`） |
| 修法 | 改数据结构 | **改那几行命令** |
| 产物 | 重新生成整份配置 | 只动必要行，其余字节不动 |

缺的就是「配置文本 ↔ 模型」这一层。

## 2 实现

新增三个文件，**没有改动原有 24 类故障的任何代码**：

```
pktlab/diag.py        解析 IOS 配置 → 模型 → 检查 → 打补丁（核心，约 400 行）
tools/diag_cfg.py     CLI：读坏配置目录，出诊断报告 + 修好的配置 + diag.jsonl
tools/make_bad_configs.py  从真实生成物「只改一处」造样本，保证样本可复现
```

流程就是判定语的四个要求：

```
parse()  →  check()  →  fix()  →  重新 parse + check
  ↑                                      │
  └──────── ≤3 轮循环 ───────────────────┘
```

每轮都把「读到什么 / 判什么 / 改了什么」写进 `diag.jsonl`，可以逐步回放。

## 3 五类故障与处理方式

| 代码 | 故障 | 怎么定位 | 自动修吗 |
|---|---|---|---|
| `RIP_MISSING_NET` | `router rip` 漏宣告直连主网络 | 由接口地址算有类主网络，比对 `network` 行 | ✅ 补 ` network <主网络>` |
| `OSPF_MISSING_NET` | 直连网段没被 `network ... area` 覆盖 | 把 wildcard 取反成掩码，判断是否包含直连网段 | ✅ 补 ` network <网段> <反掩码> area <原有 area>` |
| `MASK_MISMATCH` | 互联口两端掩码不一致 | 两地址互相落在对方掩码内、却算出不同网段 | ✅ 两端统一为「能同时装下两地址的最长前缀」 |
| `VLAN_UNDEFINED` | 端口划进 VLAN 但没建（UC-05 踩过的坑） | `switchport access vlan N` vs `vlan N` | ✅ 补 `vlan N`，插在第一个 `interface` 之前 |
| `BAD_ADDR` / `BAD_MASK` / `DUP_IP` | 地址写成网段号/广播地址、掩码不连续、同设备重复 | 逐接口解算 | ❌ **只定位**（改法不唯一） |
| `ACL_UNKNOWN` | 接口挂了 `access-group`，但 ACL 一条都没有 | 引用 vs 定义 | ❌ **只定位**（ACL 内容取决于安全意图） |

「不修」的两类是**故意的**：ACL 里该写什么、地址该改成哪个，都不是从文本里能推出来的，
猜一个反而制造新错误。这与 DSL 层那 2 类「怎么挪没有唯一答案」的故障是同一个原则。

## 4 五组实测（`python tools/test_diag.py` 全绿）

样本全部由 `tools/make_bad_configs.py` 从真实生成物「只改一处」得到：

| 样本 | 来源 | 坏在哪 | 结果 |
|---|---|---|---|
| `case1_漏network` | UC-01 | R1 的 `router rip` 少了 `network 10.0.0.0` | **1 轮**修好，修复后 R1 与原配置**逐行相同** |
| `case2_错掩码` | UC-01 | R1 的 /30 互联口写成 `255.255.255.0` | **1 轮**修好，改成 `.252`，对端未被顺手改坏 |
| `case3_VLAN未建` | UC-05 | SW0 把端口划进 VLAN 20，但没有 `vlan 20` | **1 轮**修好，补在 `interface` 之前，且**不编造 VLAN 名字** |
| `case4_ACL未定义` | UC-07 | R1 挂了 `access-group 100`，ACL 条目全删 | 定位，**0 处改动**，原文一字未动 |
| `case5_地址非法` | UC-01 | R3 业务口写成网段号 `.128/26` | 定位，**0 处改动** |

三条「该修」的样本修完还额外验了两件事：

1. **白名单**：修后的配置过 `cmdguard`（43 条白名单 / 12 条黑名单），
   拦截 0 条——不然「修好了」是假的，下不去。
2. **幂等**：把修好的再喂一遍，0 处改动——说明不是碰巧改对，而是真的收敛了。

另有反向测试：**9 个用例的正常配置跑一遍检查，必须 0 误报**。
这条比正向用例更重要——报错报多了，工具就没人敢用。

## 5 能力边界（报告里照写）

1. **只认本项目会生成的那批命令**，不是通用 IOS 解析器；不认识的行原样跳过、不误判。
2. **不做网关类检查**：`running-config` 里没有 PC，网关只在主机侧。要查得配一份拓扑，
   那是 `pktlab.accept` 的活（DSL 层）。
3. **不自动补 ACL 内容**，也不猜 VLAN 名字——改法不唯一时宁可留给人。
4. **修完的产物是配置文本**，要重新变成可双击的 pkt，仍需走 `gen.py`（YAML 通道）。
   这一步没有自动化，因为「从配置反推 DSL」等价于重写一遍解析器，收益不抵风险。
5. 修完的配置过白名单只说明**能下发**，**能不能通**仍要看验收报告——两件事不能混着说。

## 6 怎么跑

```cmd
python tools\make_bad_configs.py                     :: 重新生成 5 个样本
python tools\diag_cfg.py bad_configs\case1_漏network  :: 单个样本
python tools\test_diag.py                            :: 六组断言
```

产物在 `out/C3/<样本>/`：`诊断报告.md`、`fixed/*.cfg`、`diag.jsonl`。
