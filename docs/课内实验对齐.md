### 2.1 实验 4-10 / 4-11 号用例（B1 专用，已按手册复刻）

**证据来源**：实验手册课件已到手，**两份 pptx 的全部文字（含文本框、表格、备注页）都已提取成纯文本**，
拓扑、地址、命令、验证动作逐条照原文复刻，不是自己编的。
- `4.10 实验4-10 路由信息协议RIPv2与RIPv1的对比.pptx`（45 页）→ `out/手册_4-10.txt`
- `4.11 实验4-11 验证开放最短路径优先OSPF协议.pptx`（45 页）→ `out/手册_4-11.txt`
- 提取工具：`tools/extract_pptx_text.py`（递归读组合内文本框 + 表格单元格 + 备注页）
- 注意：4-10 的 CLI 画面是**截图**，4-11 的红字注释是**文本框**——两种都得读，只读正文会漏一半

两个实验**共用同一套拓扑和编址**，差别只在路由协议：

| | 地址 |
|---|---|
| PC0 | 192.168.16.1**/25**，网关 192.168.16.126 |
| PC1 | 192.168.16.129**/26**，网关 192.168.16.190 |
| Router0 | Gig0/0 .126/25 · Se0/0/0 30.0.0.1/30 · Gig0/1 10.0.0.1/30 |
| Router1 | Gig0/0 .190/26 · Se0/0/0 30.0.0.2/30 · Gig0/1 20.0.0.1/30 |
| Router2 | Gig0/0 10.0.0.2/30 · Gig0/1 20.0.0.2/30 |

R0—R1 走**串口**（30.0.0.0/30），R0—R2—R1 走**以太**（10.0.0.0/30 + 20.0.0.0/30）作为绕行路径。

| 用例 | 手册验证点 | 实现 | 产物 | 断言 | 检查 |
|---|---|---|---|---|---|
| **UC-80** | 第 7 步：验证 RIPv1 是有类协议、不支持 VLSM | `examples/uc410_v1.yaml` | `out/UC-80.pkt` | 2/2 | 5/5 |
| **UC-81** | 第 8、9 步：关 RIPv1、起 RIPv2 + 关自动汇总 | `examples/uc410_v2.yaml` | `out/UC-81.pkt` | 2/2 | 5/5 |
| **UC-82** | 第 5、6、9 步：OSPF 配置、路由表、按代价选路<br>第 10 步：等价负载均衡 | `examples/uc411.yaml` | `out/UC-82.pkt` | 2/2 | 5/5 |

**三个用例都已在 PT 里实测通过**（2026-10-22）：
- **UC-82** 7 项对账全一致——`Fa3/0` 参与 OSPF（cost 1、DR）、R0→`/26` `[110/3] via 10.0.0.2`、
  R0→`20.0.0.0/30` `[110/2]`、R2→`/25` 与 `/26` 各 `[110/2]`、R2 去 `30.0.0.0/30` **两条 `[110/65]`**、
  PC0 tracert **4 跳**第 2 跳 `10.0.0.2`；
- **UC-80** `send version 1, receive 1` + `Automatic network summarization is in effect`，
  PC0→PC1 `100% loss`、从第 2 个包起网关 `192.168.16.126` 回 `Destination host unreachable`；
- **UC-81** `send version 2, receive 2` + `is not in effect`，`tracert` **3 跳**、第 2 跳 `30.0.0.2`。

三者并排就是手册第 7 步与第 9 步要的完整对照：同一张网，v1 不通（有类、不支持 VLSM）、
v2 通且走 1 跳串口、OSPF 通但走 2 跳以太绕行。

**核心现象（整个实验 4-10 的考点）**：`192.168.16.0/25` 与 `192.168.16.128/26`
**同属主网络 192.168.16.0/24**。RIP v1 通告不带掩码、只发主网络，R0 和 R1 都认为
整个 /24 在自家门口，于是互相丢弃对方的路由：

| 协议 | PC0 → PC1 | 走哪条路 |
|---|---|---|
| RIP **v1** | **不通** | —（路由学不到） |
| RIP **v2**（关自动汇总） | 通 | **串口直连** R0→R1（按跳数，1 跳） |
| **OSPF**（进程 **100**，单区域 area 0） | 通 | **以太绕行** R0→R2→R1（按代价 1+1=2 < 串口 64） |

最后两行是手册第 9 步要的对照：**同一张网，RIP 走 1 跳串口，OSPF 走 2 跳绕行**。
RIP 数跳数、OSPF 算代价，这就是「OSPF 认为好的路由是路径代价最少」的直接证据。

**手册第 35 页把代价写成了 66 与 4，我们写 64 与 2，两者不矛盾**：
手册是从 PC0 算到 PC1，两端主机侧的以太口各算 1（1+64+1=66 / 1+1+1+1=4）；
我们只算路由器之间（64 / 2）。**差的那 2 是两条路径共有的**，比大小结果完全一致。

**进程号是 100，不是 1**——手册第 24 页红字注释明写「配置进程号为100的OSPF」。
初版按惯例写了 1，属于自己加戏，已按原文改为 `process: 100`，
`test_cfgprofile` 第 [4] 组现在硬性断言 `router ospf 100`。

**手册第 10 步（等价负载均衡）现在能验了**。之前判断「验不了」，是因为没算出来
两条等代价路由从哪来；手册第 39 页给的做法是**在 Router2 上 `ping 30.0.0.2`**，答案就在这：
R2 到 `30.0.0.0/30` 有两条路——经 R0（Fa2/0 代价 1 + R0 的 Se0/0 代价 64 = **65**）
或经 R1（Fa3/0 代价 1 + R1 的 Se0/0 代价 64 = **65**），
两边都是「一段以太 + 一段串口」，代价自然相等。

这一点已建模：`accept._ecmp_asserts()` 枚举同一目的网段的全部接入路由器、各自算最小代价路径，
代价相同就产出 `Ecmp` 条目；`out/UC-82_验收报告.md` 因此多出一节
「等价多路径（ECMP）断言」，`test_cfgprofile` 第 [7] 组断言
「只有 R2 出现等价多路径、代价 65、分支是 10.0.0.1/20.0.0.1」。
顺带发现 UC-02（附录要求「观察等价负载均衡」）的三角串口拓扑也是真 ECMP（代价 128），同样被算了出来。

**这两条等代价路由已在 PT 里实测看到**：R2 的 `show ip route` 出来两行
`O 30.0.0.0/30 [110/65]`，一行 `via 10.0.0.1, Fa2/0`、一行 `via 20.0.0.1, Fa3/0`，
与推算的共同代价、下一跳、出口逐项一致。所以手册第 10 步**不再是「未覆盖」**。

**型号差异，必须说明**：手册用 2911（Gig0/0、Gig0/1、Se0/0/0），本项目骨架只有
`Router-PT-Empty`（Serial0/0、Serial1/0、Fa2/0、Fa3/0）。映射 Gig0/0→Fa2/0、
Gig0/1→Fa3/0、Se0/0/0→Se0/0，端口数够、功能等价，但**接口名不同**，
在 PT 里核对时按 Fa2/0 这些名字敲。这是真实差异，不是等价替换。

**UC-80 与 UC-81 是受控对照**：设备清单、链路清单、所有接口地址完全一致，`routing` 段
只有 `version` 和 `auto_summary` 两个字段不同（测试里逐字段比对）。只有把变量锁死，
「版本差异正确体现」才有说服力。

**在 PT 里怎么验**：`docs/验证清单_UC80-81-82.md`，三个用例逐关给出要敲的命令和期望输出
（含 `show ip protocols` 的 `summarization` 判别、`show ip ospf interface brief` 的代价、
tracert 跳序、第 10 步的交替观测、第 11 步的 `debug ip ospf events`）。
写这份清单时特意避免贴整张伪造的路由表——只标出「必须有哪行」「必须没有哪行」，
因为 PT 各版本的路由表排版会变，照抄整表反而会误导人。

**实测暴露的一个生成器 bug（已修）**：第一轮实测 UC-82 时 R0 的 `Fa3/0` 起不来，
`show ip ospf interface brief` 里没有它，于是 R0 与 R2 建不起邻居、流量全走串口。
根因是设备从骨架 pkt 克隆时，端口节点里带着骨架自带的旧地址（R0 的 Serial0/0 残留 `10.0.0.1`），
PT 载入先装端口地址再回放 running-config，配置里 `Fa3/0` 也写 `10.0.0.1` → **被判 IP 冲突而拒绝**。
修法是 `Device.clear_port_ips()`：端口地址一律只由 running-config 提供，
`test_cfgprofile` 第 [8] 组守这条。这不是「手册复刻」的问题，是装配环节的问题。

## 3 UC-03 的 `O IA` 是怎么验的

附录要求「检查 R1 路由表中跨区路由的标记」。验收器为此加了一条判定：
**出口接口所在 area ≠ 目的网段所在 area → 这条路由就是跨区路由，报告里标 `O IA`**。

`out/UC-03_验收报告.md` 的路由表断言里直接能看到：

| 路由器 | 目的前缀 | 类型 | 期望条目 |
|---|---|---|---|
| R0 | 192.168.0.0/24 | 直连 | `C    192.168.0.0/24 is directly connected, FastEthernet2/0` |
| **R0** | 192.168.1.0/24 | **OSPF 跨区** | `O IA    192.168.1.0/24 [110/66] via 10.0.0.2, 00:00:12, Serial0/0` |
| R1 | 192.168.0.0/24 | OSPF | `O    192.168.0.0/24 [110/65] via 10.0.0.1, 00:00:12, Serial0/0` |
| R1 | 192.168.1.0/24 | OSPF | `O    192.168.1.0/24 [110/2] via 172.19.0.2, 00:00:12, FastEthernet2/0` |
| **R2** | 192.168.0.0/24 | **OSPF 跨区** | `O IA    192.168.0.0/24 [110/66] via 172.19.0.1, 00:00:12, FastEthernet2/0` |
| R2 | 192.168.1.0/24 | 直连 | `C    192.168.1.0/24 is directly connected, FastEthernet3/0` |

读法：R1 是 ABR，两边都是区域内路由（`O`）；R0 和 R2 学对端业务网段必须跨区（`O IA`）。
**在 PT 里敲 `show ip route` 应当看到一样的标记**，这是 UC-03 的验收点。

注意 R1 到 192.168.1.0/24 走的是 172.19 那条以太链路（开销 2 < 串口路径的 65），
所以下一跳是 172.19.0.2 —— 想看到串口那条要多加一条 `ip ospf cost` 调开销，附录没要求，没做。

## 4 UC-01「前一半」的口径问题（诚实说明）

附录原文：「左侧局域网从 192.168.16.0/24 中划出**前一半**给行政部」。
按字面，前一半是 `/25`（.0–.127），但附录同时要求「右侧划出 192.168.16.128/26 给研发部」，
而 `192.168.16.128/26` 与 `192.168.16.0/25` 是重叠的 —— **两条要求本身互相矛盾**。

我们的取舍：行政部用 `192.168.16.0/26`（.0–.63），研发部 `192.168.16.128/26`，
中间留空，两个子网不重叠、网关（.62 / .190）都是各自子网的最后一个可用地址。
`examples/uc01.yaml` 的注释里也写了这件事。

> 顺带一个观察：模型对同一句话给的答案是 `/25`（字面正确但不能与 /26 共存），
> 说明**需求本身有歧义时，模型和人都可能各取一半** —— 这一条已写进 `docs/D2_失败案例分析.md` 第 9 节。

## 5 UC-05 方案二为什么没有 pkt（能力边界）

`.pkt` 装配器是「**基于种子文件只删不增**」：骨架里只有 `Router-PT-Empty` / `2960-24TT` / `PC-PT`
三种设备槽位，**没有 3560 这类三层交换机**。新增一个设备型号需要克隆整棵 `<MODULE>` 树，
并重建 `SAVE_REF_ID` / `MEM_ADDR` 以及所有引用它的 `<LINK>` —— 这是已知限制，不是这次偷懒。

所以方案二交付的是**完整可粘贴的配置 + 手工搭建步骤 + 7 步验证清单**
（`docs/UC-05_方案二_三层交换机SVI.md`），并且明确写「方案二不在自动化验收范围内」。

**没有把它包装成「也自动生成了」。**

## 6 没做的三个用例（也是 D1 的一部分，说明为什么不影响判定）

| UC | 状态 | 理由 |
|---|---|---|
| UC-04 NAT | ❌ 不支持 | DSL 没有 NAT 字段。报告里明确写「不支持」，不半吊子实现（`ip nat inside source` 会被命令白名单拒绝，见 `docs/E_命令级护栏.md`） |
