# UC-80 / 81 / 82 在 Packet Tracer 里的验证清单

对应实验手册 **4-10**（RIPv2 与 RIPv1 的对比）与 **4-11**（验证 OSPF）。
三个用例共用同一套拓扑和编址，**只有路由协议不同**——这是刻意的，是为了让「协议差异」成为唯一变量。

| 文件 | 跑的是什么 | 结论应该是什么 |
|---|---|---|
| `out\UC-80.pkt` | RIP **v1**（有类，自动汇总） | PC0 ↔ PC1 **不通** |
| `out\UC-81.pkt` | RIP **v2** + `no auto-summary` | 通，走 **1 跳串口** |
| `out\UC-82.pkt` | **OSPF** 单区域 area 0 | 通，走 **2 跳以太绕行** |

---

## 拓扑与编址

```
PC0 ── SW0 ── R0 ══串口 30.0.0.0/30══ R1 ── SW1 ── PC1
               │                      │
               └── 10.0.0.0/30 ── R2 ── 20.0.0.0/30 ──┘
```

| 设备 | 接口 | IP / 掩码 | 说明 |
|---|---|---|---|
| PC0 | — | 192.168.16.1 **/25** | 网关 192.168.16.126 |
| PC1 | — | 192.168.16.129 **/26** | 网关 192.168.16.190 |
| R0 | **Fa2/0** | 192.168.16.126/25 | 手册写 Gig0/0 |
| R0 | **Fa3/0** | 10.0.0.1/30 | 手册写 Gig0/1 |
| R0 | **Se0/0** | 30.0.0.1/30 | 手册写 Se0/0/0 |
| R1 | **Fa2/0** | 192.168.16.190/26 | |
| R1 | **Fa3/0** | 20.0.0.1/30 | |
| R1 | **Se0/0** | 30.0.0.2/30 | DCE 端，已配 `clock rate 2000000` |
| R2 | **Fa2/0** | 10.0.0.2/30 | |
| R2 | **Fa3/0** | 20.0.0.2/30 | |

> **接口名不一样，这点必须先说清楚。** 手册用 2911（`Gig0/0`、`Gig0/1`、`Se0/0/0`），
> 本项目骨架只有 `Router-PT-Empty`（**Fa2/0、Fa3/0、Se0/0、Se1/0**）。
> 映射是 Gig0/0→Fa2/0、Gig0/1→Fa3/0、Se0/0/0→Se0/0，端口数够、功能等价，
> 但**敲命令时用 Fa2/0 这些名字**，别照着手册敲 Gig0/0，PT 会报 `% Invalid input`。

---

## 开跑前两件事

1. **确认在 Realtime 模式**（右下角时钟，不是 Simulation 秒表）。
   仿真模式下 ping 要手动点播放，容易误判。
2. **打开后等 30 秒**再测。RIP 每 30 秒发一次更新，**第一次 ping 不通很可能是还没收敛**。
   判「不通」之前，先在 R0 上 `show ip route` 确认它到底学到了什么——这一步比 ping 有说服力。

**串口线是红色的，这是正常的**（串行链路在 PT 里固定显示红色），不要当成故障。

---

## 第 0 关：确认你打开的是**新** pkt（30 秒，跳过这关会白测一轮）

这一关是有来历的：第一轮实测的截图里，路由器配置是
`Fa2/0 192.168.1.62 255.255.255.192` + `network 192.168.1.0`、
`Serial0/0 11.0.0.1 255.0.0.0`、OSPF 还有 `area 1`——那是**旧版**用例
（不同主网 + 2 台路由器），跟 `out\UC-80.pkt` 里实际的
`192.168.16.126/25` + 3 台路由器不是一回事。

**原因不是生成错，是 PT 窗口还开着旧文件**：PT 打开 pkt 后，内容读进内存，
磁盘上的文件被重新生成，**已经开着的窗口不会跟着变**。

所以：**先完全退出 Packet Tracer（不是关文件标签，是退出程序），再双击重开。**

打开后照这张表核对，任何一项对不上就说明看的是旧文件：

| 看什么 | 新文件（对） | 旧文件（错） |
|---|---|---|
| 路由器台数 | **3 台**：`R0`、`R1`、`R2` | 2 台：`R1`、`R2` |
| R0 的 `Fa2/0` | `192.168.16.126 / 255.255.255.128` | `192.168.1.62 / 255.255.255.192` |
| R1 的 `Fa2/0` | `192.168.16.190 / 255.255.255.192` | — |
| PC 的 ping 目标 | `192.168.**16**.129` | `192.168.2.10` |
| RIP 的 network | `192.168.16.0` + `10.0.0.0` + `30.0.0.0` | `192.168.1.0` + `10.0.0.0` |
| OSPF（UC-82） | `router ospf **100**`；全部 `area 0`；反掩码 `0.0.0.127` / `0.0.0.63` / `0.0.0.3` | 有 `area 1`；`0.0.0.255` |

另外两个不是故障的现象，先说一下免得白查：

- **`show run | section router rip` 在 PT 里不支持**，会报
  `% Invalid input detected at '^' marker`。这是 PT 的 12.2 没有 `| section` 过滤器，
  **不是配置坏了**。要看 RIP 就用 `show ip protocols`（最直接），或者 `show running-config` 整页翻。
- `show run` 里空接口没有 `ip address` 那一行是正常的（PT 不显示默认值）。

### 这一关救过一次命：R0 的 Fa3/0 起不来

第一轮实测 UC-82 时，R0 的 `show ip ospf interface brief` **只有 Fa2/0 和 Se0/0，
没有 Fa3/0**，于是 R0 与 R2 建不起邻居，流量全走串口（`tracert` 只有 3 跳、代价 65）。

根因不在配置里，在**生成器**：设备是从骨架 pkt 克隆的，端口节点里带着骨架自带的旧地址
（R0 的 Serial0/0 残留 `10.0.0.1`）。PT 载入时先装端口地址、再回放 running-config，
而配置里 `FastEthernet3/0` 也写 `10.0.0.1` —— **后写的那个撞上还在的旧地址，被判 IP 冲突而拒绝**，
表现就是「`show run` 里有这一行，接口却没有地址、也不进 OSPF」。

已修：`assemble.build()` 现在先调 `Device.clear_port_ips()` 把端口节点里的残留地址清空，
地址只由 running-config 提供；`test_cfgprofile` 第 [8] 组专门守这一条。

**所以拿到新 pkt 后，如果 OSPF 邻居少一个，先看是不是端口没起来**——
现在应该不会再发生了，但这条排查路径记在这里。

# UC-80：RIPv1 —— 应该不通

> 考点：`192.168.16.0/25` 和 `192.168.16.128/26` **同属主网络 192.168.16.0/24**。
> v1 通告不带掩码、只发主网络，两边的路由器都认为整个 `/24` 在自家门口，于是互相丢弃对方的路由。

## 第 1 关：版本与汇总

点 **R0** → `CLI` → 回车 → `enable` → 然后：

```
show ip protocols
```

要看到这两行（其余不用管）：

```
Default version control: send version 1, receive version 1 2
Automatic network summarization is in effect
```

**第二行是这一关的关键。** `is in effect` = 自动汇总开着 = v1 的行为。
如果这里显示 `is not in effect`，说明生成器配错了（应该配不出来，出了就告诉我）。

## 第 2 关：路由表里「缺了什么」（这一步才是证据）

R0 上继续：

```
show ip route
```

**要确认「有」这一行**（直连自己的子网，掩码是真实的 /25）：

```
C    192.168.16.0/25 is directly connected, FastEthernet2/0
```

**要确认「没有」这两种行**（这是 v1 学不到的证据）：

```
R    192.168.16.0/24 ...        ← 不该有一整条主网络
R    192.168.16.128/26 ...      ← 不该有对端子网
```

整张表里**不应该**出现任何指向 `192.168.16.128/26` 的条目。

> 顺带会看到 `R  20.0.0.0/8` 这样的条目——那是 R1 把 `20.0.0.0/30` 汇总成了主网络 `/8`
> （20.x 是 A 类地址），属于 v1 的正常行为，跟你这次要看的东西无关，**不用管它**。

如果你真的看到了 `R    192.168.16.0/24 [120/1] via 30.0.0.2`，那说明 PT 这版
对 v1 的处理跟我们模型不一样——请截图给我，我改验收器的建模，不改结论去凑。

R1 上敲同样的命令，应该看到**直连 /26、缺 /25**，镜像对称。

## 第 3 关：R2 学到了什么（旁证）

点 **R2** → `show ip route`：

```
R    192.168.16.0/24 [120/1] via 10.0.0.1, ... FastEthernet2/0
R    192.168.16.0/24 [120/1] via 20.0.0.1, ... FastEthernet3/0
```

**R2 不在主网络上，所以它照单全收**——两条都学到，汇总成一条 `/24`。
（PT 可能只显示一行、并列两个下一跳，也可能显示两行，都算对。
关键看：**前缀是 `/24` 不是 `/25` 或 `/26`**，这就是有类汇总在起作用。）

## 第 4 关：ping（结论）

PC0 → `Desktop` → `Command Prompt`：

```
ping 192.168.16.129
```

期望**不通**，且报错形式是这个（来自网关，不是超时）：

```
Reply from 192.168.16.126: Destination host unreachable.
```

**为什么会是 `Destination host unreachable` 而不是 `Request timed out`**：
PC0 把包发给了网关 R0，R0 路由表里没有去 `192.168.16.128/26` 的路由，
直接在本地回一条 ICMP 不可达。**这条报错本身就是「R0 没有路由」的证据**，
比 `Request timed out` 更能说明问题出在哪。

再反过来测一次，PC1 上 `ping 192.168.16.1`，期望同样不通、
报错来自 `192.168.16.190`。

## UC-80 通过标准

- [x] `show ip protocols` → `Default version control: send version 1, receive 1`
- [x] `show ip protocols` → `Automatic network summarization is in effect`
- [ ] R0 的 `show ip route` **没有**去 `192.168.16.128/26` 的路由
- [ ] R1 的 `show ip route` **没有**去 `192.168.16.0/25` 的路由
- [ ] R2 学到的是 `192.168.16.0/**24**`（汇总后的主网络）
- [x] PC0 → PC1 **不通**，报错来自 `192.168.16.126`

**实测记录（2026-10-22）**：`show ip protocols` 三项全中——
`send version 1, receive 1`、`Automatic network summarization is in effect`、
`Routing for Networks` 是 `10.0.0.0 / 30.0.0.0 / 192.168.16.0` 三条有类地址。

`ping` 的实测输出**和预期略有出入，但更好**：

```
Request timed out.                                   ← 第 1 个包
Reply from 192.168.16.126: Destination host unreachable.   ← 第 2、3、4 个
Packets: Sent = 4, Received = 0, Lost = 4 (100% loss)
```

第 1 个包是 `Request timed out` 而不是 `unreachable`，因为那一刻 PC0 还没学到网关的 MAC
（ARP 未完成，包根本没出去）。**从第 2 个包起就稳定是「网关回不可达」**——
这就是 R0 路由表里没有 /26 的直接证据。写报告时把这一条说清楚，别让人以为 100% 丢包就等于没配通。

> **手册第 6 步的「选择要监视的网络协议」和「第 8 步的 `no router rip`」我没有做成关卡**，
> 原因：它们是操作手法，不是结论。
> - 第 6 步是在 **Simulation 模式**下勾 IPv4 → ICMP + RIP，用来**看** RIP 更新包怎么走。
>   如果你要给报告配图，可以这么点：右下角 `Simulation` → `Edit Filters` → `IPv4` 选项卡 → 勾 `ICMP`、`RIP`。
> - 第 8 步是在三台路由器上各敲一次 `no router rip`，把 v1 清掉，为第 9 步起 v2 做准备。
>   我们的做法是**另存两个 pkt**（UC-80 一个、UC-81 一个），所以不需要这条命令——
>   真要在同一个 pkt 里演示「v1→关闭→v2」，就照手册敲 `no router rip` 再配 v2。

# UC-81：RIPv2 + no auto-summary —— 应该通，走串口

## 第 1 关：版本与汇总（跟 UC-80 正好反过来）

R0 上 `show ip protocols`：

```
Default version control: send version 2, receive version 2
Automatic network summarization is not in effect
```

**`is not in effect`** —— 这两个用例的差别就在这个词上。

## 第 2 关：路由表里有精确前缀

R0 上 `show ip route`：

```
R    192.168.16.128/26 [120/1] via 30.0.0.2, ... Serial0/0
```

**三个要点**：

1. **前缀是 `/26`**，不是 `/24` —— 不汇总了，VLSM 信息保住了
2. **`[120/1]`** —— 度量 1 跳，直接走串口
3. **出口是 `Serial0/0`** —— 没有绕 R2

R1 上对称：`R 192.168.16.0/25 [120/1] via 30.0.0.1, Serial0/0`。

## 第 3 关：ping

PC0 上 `ping 192.168.16.129`，期望：

```
Reply from 192.168.16.129: bytes=32 time=... TTL=126
```

**TTL 126** = 初始 128 减 2 跳（经过 R0、R1 两台路由器）。
如果 TTL 是 127，说明只过了一台路由器，拓扑或线路有问题。

## 第 4 关：tracert（确认走的是串口）

```
tracert 192.168.16.129
```

期望**3 行**：

```
    1   192.168.16.126      <- R0 的 Fa2/0（PC0 的网关）
    2   30.0.0.2            <- R1 的 Se0/0（串口对端）
    3   192.168.16.129      <- 目的主机
```

**第 2 跳是 `30.0.0.2` 就对了** —— 说明 R0 把包从串口发出去，没绕 R2。
（跳序规则：每一行是「接收该包的那个接口的地址」，最后一行是目的主机。）

## UC-81 通过标准

- [x] `show ip protocols` → `Default version control: send version 2, receive version 2`
- [x] `show ip protocols` → `Automatic network summarization is not in effect`
- [ ] R0 有 `R 192.168.16.128/26 [120/1] via 30.0.0.2`，出口 `Serial0/0`
- [ ] PC0 ↔ PC1 **通，TTL=126**
- [x] `tracert` 第 2 跳是 **`30.0.0.2`**（串口），共 **3 行**

**实测记录（2026-10-22）**：`send version 2, receive 2` + `Automatic network summarization is not in effect`
都对上了，和 UC-80 的 `is in effect` 正好构成一对。

`tracert 192.168.16.129` 实测 **3 跳**：`192.168.16.126 → 30.0.0.2 → 192.168.16.129`，
第 2 跳就是串口对端 —— 说明 v2 关掉汇总后，`/26` 这个 VLSM 子网真的传过来了。

### ⚠️ `Routing Information Sources` 那张表别当真

UC-81 的 `show ip protocols` 里，`Routing Information Sources` **只列了 `10.0.0.2`**（R2），
没有 `30.0.0.2`（R1）。看起来像「没收到 R1 的更新」，但 `tracert` 第 2 跳明明就是 `30.0.0.2`——
说明 R1 的更新**收到了、也用了**（不然不会有经 R1 的路由）。

这是 PT 这张表的显示口径问题：UC-80 同样拓扑下它列了两个源，UC-81 只列一个，
配置本身只差 `version` 和 `no auto-summary` 两个字段。
**所以判「有没有学到路由」要看 `show ip route`，不要看 `show ip protocols` 的这张表。**

> 想要更硬的证据，可以补一张 UC-81 的 `show ip route`：
> 应该看到 `R 192.168.16.128/26 [120/1] via 30.0.0.2, Serial0/0`（精确 /26、1 跳、走串口）。
> UC-80 也可以补一张，应该**看不到**任何 `/26` 的 R 条目。

## 4-10 实测结论：v1 不通、v2 通的对照成立（2026-10-22）

| 项目 | UC-80（RIPv1） | UC-81（RIPv2 + no auto-summary） |
|---|---|---|
| `show ip protocols` 版本行 | `send version 1, receive 1` | `send version 2, receive 2` |
| 自动汇总 | **`is in effect`** | **`is not in effect`** |
| `Routing for Networks` | `10.0.0.0 / 30.0.0.0 / 192.168.16.0` | 同（三条有类地址） |
| PC0 → PC1 | **100% 丢包**，第 2~4 个包回「网关不可达」 | 通，`tracert` 3 跳 |
| `tracert` 第 2 跳 | —（断在第 1 跳） | **`30.0.0.2`**（串口） |

两个用例的 pkt 拓扑、编址、接口名完全一致，`routing` 段只差 `version` 与 `no auto-summary` 两个字段。
**这就是手册第 7 步与第 9 步要的那组对照**：同一张网，v1 因为是有类协议、不支持 VLSM 而不通，
换 v2 关掉自动汇总就通了，而且走的是 1 跳串口直连。

# UC-82：OSPF —— 应该通，但走另一条路

> 这个用例最有意思的地方：**同一张网，RIP 走 1 跳串口，OSPF 走 2 跳以太绕行。**
> 原因是 RIP 数跳数、OSPF 算代价——串口带宽 1544 kbps 代价 64，以太 100 Mbps 代价 1。

## 第 1 关：邻接起来了

R0 上：

```
show ip ospf neighbor
```

期望三台两两相邻（R0 有 2 个邻居：R1 走串口、R2 走以太）：

```
Neighbor ID     Pri   State       Dead Time   Address      Interface
20.0.0.2          1   FULL/  -    00:00:3x    30.0.0.2     Serial0/0
30.0.0.2          1   FULL/  -    00:00:3x    10.0.0.2     FastEthernet3/0
```

（`Neighbor ID` 是对方最大的 IP 或 router-id，数字会不一样，**只看 State 列是 `FULL/`**。）

如果状态停在 `INIT` / `EXSTART` / `2WAY`，等 30–60 秒；一直不动就是 area 或反掩码配错了。

### ⚠️ 40 秒 WAIT 状态：最容易误判成故障的一条

刚打开 pkt 时，R0 的以太口会显示 `State = WAIT`、`Nbrs F/C = 0/0`，
**这不是没配好**。OSPF 在广播型网络（以太网）上要先等 **40 秒**的 DR/BDR 选举定时器
（`wait timer`），才会进入 `DR`/`BDR`/`DROTHER` 并开始和邻居建立 FULL 邻接。

同一时刻两台设备的画面可能对不上：R2 的日志已经写着 `Nbr 192.168.16.126 ... FULL`，
R0 的 `show ip ospf interface brief` 还停在 `WAIT` —— 因为 R0 那张图是在 40 秒内截的。

**所以：打开 pkt 后先等满 60 秒再敲任何 `show` 或 `tracert`。**

实测踩过两次，同一台 PC0、同一个 pkt，前后两次 `tracert` 差 3 分钟：

```
第一次（刚开 pkt）            第二次（收敛后）
1  192.168.16.126             1  192.168.16.126
2  30.0.0.2      ← 串口        2  10.0.0.2      ← 绕行
3  192.168.16.129             3  20.0.0.1
                              4  192.168.16.129
```

**`Nbrs F/C` 这一列在 PT 里不靠谱**——实测 R0 与 R1 的串口邻接早已 `FULL`，
`Se0/0` 那行仍然显示 `0/0`；Fa3/0 与 R2 的邻接也 `FULL`，同样显示 `0/0`。
这一列在 PT 的 `show ip ospf interface brief` 里基本没填，**别拿它判邻居**。
要判邻接就用 `show ip ospf neighbor`（看 `FULL/`），或者直接看路由表里有没有那条绕行路由。

## 第 2 关：代价（这是选路的依据）

R0 上：

```
show ip ospf interface brief
```

期望（**PID 列是 100**，因为手册指定进程号 100；`State` 是收敛后的值）：

```
Interface    PID   Area    IP Address/Mask      Cost  State  Nbrs F/C
Fa3/0        100   0       10.0.0.1/30          1     DR     0/0
Fa2/0        100   0       192.168.16.126/25    1     DR     0/0
Se0/0        100   0       30.0.0.1/30          64    POINT  0/0
```

（上面是 2026-10-22 实测到的真实输出。注意**顺序不一定是 Fa2/0 打头**，
PT 按接口名排序，`Fa3/0` 排在 `Fa2/0` 前面是正常的；`Se0/0` 的 State 是 `POINT` 不是 `P2P`。）

三个要点：

1. **必须有三行**。第一轮实测少了 `Fa3/0`（生成器端口残留地址撞车，已修，见第 0 关末尾）。
2. **`State` 收敛后是 `DR`**（`Fa3/0`、`Fa2/0` 都是），串口是 `POINT`。
3. `Nbrs F/C` 在 PT 里基本不填（实测 FULL 了也显示 `0/0`），**别用它判邻居**。

**读法**：以太口 `Cost 1`，串口 `Cost 64`（1544 kbps → 100000/1544 = 64）。
去 `/26` 走串口要 64+1=65，走以太绕一圈只要 1+1+1=3 → **OSPF 必然选绕行**。

> 如果这里串口显示 `Cost 50`（按 clock rate 2 Mbps 算 = 100/2）或别的值，
> 说明 PT 这版算带宽的口径不同。**那也会选绕行，结论不变**，但请截图给我记一笔。

**全部应该是 `Area 0`** —— 手册 4-11 是单区域，看到 `Area 1` 就配错了。

## 第 3 关：路由表

R0 上 `show ip route`，**实测到的完整相关行**（2026-10-22 复测）：

```
C    10.0.0.0 is directly connected, FastEthernet3/0
O    20.0.0.0 [110/2] via 10.0.0.2, ... FastEthernet3/0
C    30.0.0.0 is directly connected, Serial0/0
C    192.168.16.0/25 is directly connected, FastEthernet2/0
O    192.168.16.128/26 [110/3] via 10.0.0.2, ... FastEthernet3/0
```

**三个要点**：

1. **去 `/26` 是 `[110/3]` 且出口 `FastEthernet3/0`、下一跳 `10.0.0.2`** —— 朝 R2，不走串口。
   代价 3 = R0 出口以太 1 + R2 出口以太 1 + **R1 面向 `/26` 那个口 1**。
   最后那 1 是最容易算漏的：Cisco 的代价要算到「目的网段所接的那个接口」。
2. **去 `20.0.0.0/30` 是 `[110/2]` 走 `10.0.0.2`** —— 也是绕行（1+1），不是走串口 64+1。
   这一条比重更狠：连 R2 所在的网段都不从串口去。
3. **`C 10.0.0.0 ... FastEthernet3/0` 必须有** —— 没有这一行就说明 Fa3/0 没起来（见第 2 关）。

这条就是「OSPF 按代价选路」的直接证据：明明有 1 跳的串口直连，它不走。

## 第 4 关：tracert（跟 UC-81 对比着看）

PC0 上 `tracert 192.168.16.129`，期望**4 行**（比 UC-81 多一行）：

```
    1   192.168.16.126      <- R0 Fa2/0（网关）
    2   10.0.0.2            <- R2 Fa2/0
    3   20.0.0.1            <- R1 Fa3/0
    4   192.168.16.129      <- 目的主机
```

**第 2 跳变成 `10.0.0.2`**，这就是全部的重点。
把 UC-81 和 UC-82 的 tracert 结果并排放，一个 3 行、一个 4 行，
一个走串口、一个绕以太 —— 这一对截图就是实验报告里最有说服力的东西。

> **已实测通过**（2026-10-22）：同一台 PC0、同一个 pkt，等收敛后 `tracert` 输出
> `192.168.16.126 → 10.0.0.2 → 20.0.0.1 → 192.168.16.129`，4 行。
> 收敛前那次是 3 行、第 2 跳 `30.0.0.2`，两次输出都在同一张截图里，正好当「收敛前后」的对照。

## 第 5 关：ping

```
ping 192.168.16.129
```

通，**TTL=125**（128 − 3 跳：R0、R2、R1）。
比 UC-81 的 126 少 1，因为多过了一台路由器 —— **这个 1 的差值就是「绕行」的量化证据**。

## 第 6 关：等价负载均衡（手册第 10 步，**这次能验了**）

> 之前我以为这一步验不了（以为两条路径代价不等）。拿到手册第 39 页才看明白：
> **不是让 PC0→PC1 走两条路，而是在 Router2 上 `ping 30.0.0.2`。**

原因是 R2 到 `30.0.0.0/30` 有两条**恰好等代价**的路：

| 路径 | 代价 |
|---|---|
| R2 → R0（Fa2/0，1）→ R0 的 Se0/0（**64**） | **65** |
| R2 → R1（Fa3/0，1）→ R1 的 Se0/0（**64**） | **65** |

两边都是「一段以太 + 一段串口」，所以相等。这就是手册为什么挑 `30.0.0.2` 这个地址。

**怎么测**：

1. 点 **R2** → CLI → `enable`
2. `show ip route`，找 `30.0.0.0/30` 那一条 —— 应该出现**两行同前缀、不同下一跳**：

```
O    30.0.0.0/30 [110/65] via 10.0.0.1, ... FastEthernet2/0
O    30.0.0.0/30 [110/65] via 20.0.0.1, ... FastEthernet3/0
```

> **这两行已经在 PT 里实测看到了**（2026-10-22 第二轮复测，R2 的 `show ip route`）。
> 也就是说「两条等代价路由」这个前提是实际成立的，不是推算出来的。剩下的只是「会不会交替」。

3. 切到 **Simulation** 模式，右侧 Event List 过滤器只勾 **ICMP**
4. R2 上敲 `ping 30.0.0.2`（手册原话是 `Router#ping 30.0.0.2`）
5. 看 Event List 里连续两个 ICMP 包的出口：**一个走 Fa2/0、一个走 Fa3/0，交替出现**

**这一步的判定标准**：`[110/65]` 两行 + 出口交替。
只要看到交替，等价负载均衡就是真的成立，不是「差不多」。

> 我们这个用例的三台路由器里，**只有 R2 会出现等价多路径**。
> R0 和 R1 去对端业务网段时，绕行 2 明显小于串口 64，没有第二条等代价的路。
> 报告里「等价多路径（ECMP）断言」一节就是这条推算结果。

## UC-82 实测结论：模型与 PT 逐项对齐（2026-10-22）

| 项目 | 验收器推算 | PT 实测 | 一致 |
|---|---|---|---|
| `Fa3/0` 是否参与 OSPF | 有，cost 1 | 有，`10.0.0.1/30` cost 1，`DR` | ✓ |
| R0 → `192.168.16.128/26` | `O [110/3] via 10.0.0.2, Fa3/0` | `O [110/3] via 10.0.0.2, Fa3/0` | ✓ |
| R0 → `20.0.0.0/30` | `O [110/2] via 10.0.0.2` | `O [110/2] via 10.0.0.2, Fa3/0` | ✓ |
| R2 → `192.168.16.0/25` | `O [110/2] via 10.0.0.1` | `O [110/2] via 10.0.0.1, Fa2/0` | ✓ |
| R2 → `192.168.16.128/26` | `O [110/2] via 20.0.0.1` | `O [110/2] via 20.0.0.1, Fa3/0` | ✓ |
| R2 → `30.0.0.0/30`（等价多路径） | 两条 `[110/65]`（10.0.0.1 / 20.0.0.1） | 两条 `[110/65]`（Fa2/0 / Fa3/0） | ✓ |
| PC0 → PC1 的 tracert | 4 跳，第 2 跳 `10.0.0.2` | 4 跳，第 2 跳 `10.0.0.2` | ✓ |

**这是「静态推算 ≠ 跑过」那条边界上第一次完全对上的用例**，
包括手册第 10 步的等价负载均衡（两条等代价路由是实测看到的，不是我算出来的）。

## 三个用例并排对照（贴进报告的那张表）

下表**除标注「推算」的两项外，其余都是 2026-10-22 在 PT 里实测到的值**：

| | UC-80 RIPv1 | UC-81 RIPv2 | UC-82 OSPF |
|---|---|---|---|
| 版本 / 进程号 | `send version 1, receive 1` | `send version 2, receive 2` | `router ospf **100**` |
| 自动汇总 | **`is in effect`** | **`is not in effect`** | —（不做有类汇总） |
| R0 有去 `/26` 的路由 | **没有**（网关回不可达） | 有 | 有 |
| 度量 | — | `[120/**1**]` 跳数 | `[110/**3**]` 代价 |
| 出口 | — | `Serial0/0` | `FastEthernet3/0` |
| PC0→PC1 | **不通**，`Received = 0, Lost = 4 (100% loss)` | 通 | 通 |

## 不通的时候按这个顺序查

| 症状 | 最可能原因 | 在哪看 |
|---|---|---|
| UC-80 竟然通了 | 生成器把 v1 写成 v2 了 | R0 `show ip protocols` 看 version 和 summarization |
| UC-81 不通 | 收敛没完成 / 汇总没关 | 等 30 秒；R0 `show ip protocols` 看 `not in effect` |
| UC-81 通了但走 R2 | 串口没 up，走的是绕行 | R0 `show ip interface brief` 看 `Se0/0` 是否 `up/up` |
| 串口一直 down | DCE 端没 clock rate（生成器已配，除非你手工改过） | R1 `show controllers serial 0/0` |
| UC-82 邻居不到 FULL | area 不一致 / 反掩码写错 | 两边 `show ip ospf interface brief` 对比 Area 列 |
| UC-82 走串口而不是绕行 | 代价算得不对（可能串口带宽被改过） | R0 `show ip ospf interface brief` 看 Cost 列 |
| ping 全丢但路由表对 | ACL / 主机网关填错 | PC `Desktop` → `IP Configuration` |
| `% Invalid input` | 把手册的 `Gig0/0` 敲到 PT 里了 | 用 `Fa2/0`、`Fa3/0` |
