# pkt 静态一致性校验器（PT 打不开问题的根因与根治）

> 对应工具：`tools/verify_pkt.py`（校验器）、`tools/test_pkt.py`（自测）、
> `pktlab/clone.py`（设备块克隆）、`tools/make_seed.py`（扩容骨架）。
> 自测套件第 8 套：`selftest.cmd`。

## 一、现象

实验 8-1 的园区网（21 台设备）第一次生成出来，**PT 点开就弹窗**：

```
This file requires Cisco Packet Tracer version 8.2.2.0400.
Your current version is 9.0.1.0858.
```

生成器全程无报错，验收器 14/14 通过，报告也出齐了 —— 但文件在 PT 里打不开。
这类 bug 最难查：报错在最后一步，病因在很前面。

## 二、排查过程

### 2.1 先排除「版本号」这个表象

弹窗里写的是版本号，第一反应是版本不兼容。但对不上：

- 顶层 `<VERSION>` 写的是 `8.2.2.0400`，与能正常打开的 UC-82 **完全相同**；
- 本机装的 PT 是 9.0.1，它自己带的 293 个示例文件里有 15 个是 8.2.x 版本的 ——
  **PT 9 能开 8.2.x 文件**。

所以版本号只是表象：PT 解析失败时弹这个窗，是它的通用错误提示。

### 2.2 对照实验：加密路径无损

把能正常打开的 UC-82 原样走一遍 `write_pt_file` 重写，字节 sha256 完全一致：

```
原文件 sha256: 04b9f541786fcd6ed648b135a7023522 48497
重写后 sha256: 04b9f541786fcd6ed648b135a7023522 48497
字节完全一致: True
```

容器编码（qCompress + Twofish-EAX）没问题。**问题 100% 在 XML 内容上**。

### 2.3 找到真正的差异：克隆出来的设备

园区网骨架是从 13 台的种子**复制设备块**扩容来的（要 21 台）。
逐字段对比「原设备」和「克隆设备」，发现克隆时只改了两处：
名字、`SAVE_REF_ID`。而**其余 11 个身份标识全都和模板设备一模一样**：

| 字段 | 现象 |
|---|---|
| `MEM_ADDR` | 3 台路由器共用 `1024025616`，6 台 PC 共用 `139852504442816` |
| `DEV_ADDR` | 3 台路由器共用 `139850972786624`，6 台 PC 共用 `139852504363984` |
| `MACADDRESS` / `BIA` | 6 台 PC 共用 `0001.9696.111D` |
| `IPV6_LINK_LOCAL` | 同一个值（它是从 MAC 推导的，MAC 没换它也不该换） |
| `PHYSICAL` 末位 uuid | 克隆设备与模板设备共用同一个物理节点 id |
| `SERIALNUMBER` | 直接重复 |
| `SAVE_REF_ID` | **前缀丢了** —— 原文件是 `save-ref-id:123…`，克隆成了裸数字 `123…` |

**PT 载入 .pkt 时是按这组身份标识建索引的**（不是按名字）。多台设备共用一个
身份 → 索引冲突 → 拒绝加载。

对照 PT 9.0.1 自己写的 18 设备文件（`saves/` 目录），全部满足：
`MEM_ADDR` 18/18 唯一、`DEV_ADDR` 18/18 唯一、MAC 189/189 唯一、
`SAVE_REF_ID` 全带 `save-ref-id:` 前缀、每台设备都在物理视图注册。

## 三、修复

### 3.1 克隆要换全套身份标识（`pktlab/clone.py`）

新建模块，把「一台设备在 .pkt 里的身份标识」列成清单，逐项重分配：

- `SAVE_REF_ID` → 新的 20 位数字，**保留 `save-ref-id:` 前缀**
- `MEM_ADDR` / `DEV_ADDR` → 新号段，且避开文件里已用的
- `MACADDRESS` + `BIA` → 新的、跨设备唯一的 MAC
  - 同一设备内多个口共用一个 MAC 的情况要**保持**（路由器三个口共用一个是 PT 自己的写法）
  - 厂商 OUI 不动，只改设备序号
- `IPV6_LINK_LOCAL` / `IPV6_DEFAULT_LINK_LOCAL` → 跟着新 MAC 重算
  - 用 modified EUI-64：MAC 第一个字节 U/L 位取反、中间接 `ff:fe`、前缀 `fe80::`
  - 验证：`0001.9696.111D` → `FE80::201:96FF:FE96:111D`，与 PT 原生文件逐字节一致
  - **顺序坑**：必须先算 IPv6 地址、再换 MAC。反过来的话，换完 MAC 再用
    「旧 MAC → 新 MAC」的映射表去查就查不到了，结果 MAC 换了、IPv6 还是旧的
- `PHYSICAL` 末位 uuid → 新的 uuid
- `SERIALNUMBER` → 新的

### 3.2 物理视图要同步注册

`PHYSICALWORKSPACE` 是一棵 NODE 树（Intercity → Home City → Corporate Office
→ Main Wiring Closet → Rack → 各设备）。每台设备在里面要有一个 NODE，
`UUID_STR` 与设备块 `PHYSICAL` 链末位**必须一致** —— 这是 PT 的对账依据。

- 路由器/交换机挂 `Rack` 下，PC 挂 `Corporate Office` 下
- NODE 的**缩进**要和同容器的兄弟节点一致，否则 PT 解析层级错位，
  设备的 uuid 会归属到容器头上（表现为「PC 挂到了 Corporate Office 头上」）
- 容器是嵌套的，`<CHILDREN>` 也要数深度配对 —— 用非贪婪正则会停在内层那个
  `</CHILDREN>` 上，位置全错

### 3.3 改名与删除要同步物理视图

- 改名：按 **uuid** 定位物理视图里的 NODE 再改名（按名字找不行，改名前后名字本来就不同）
- 删设备：连带删掉物理视图里的 NODE，否则删掉的设备还留在机架图上

> 顺带确认一件事：**PT 用 uuid 对账，不用名字**。所以「设备改名」是合法的
> （生成器正是靠改名把骨架设备映射成 DSL 里的设备名），名字对不上不影响加载。

### 3.4 版本号

新种子统一写 `9.0.0.0000`（PT 9.0.1 自己写的文件的版本号）。
但这**不是**修复打不开的关键 —— 8.2.x 也能开。

## 四、根治：把「PT 会拒绝的写法」变成静态检查

查这个 bug 花的时间比写生成器还长。所以写了 `tools/verify_pkt.py`，
把 PT 的隐性约束变成可自动拦截的规则：

| # | 检查项 | 严重度 |
|---|---|---|
| 1 | `SAVE_REF_ID` 缺 `save-ref-id:` 前缀 | 错误 |
| 2 | `SAVE_REF_ID` 重复 | 错误 |
| 3 | `MEM_ADDR` 重复 | 错误 |
| 4 | `DEV_ADDR` 重复 | 错误 |
| 5 | 物理视图里找不到设备的 `PHYSICAL` 末位 uuid | 错误 |
| 6 | 链路 `<FROM>`/`<TO>` 引用的设备 id 解析不到 | 错误 |
| 7 | MAC 跨设备重复 | 警告 |
| 8 | IPv6 链路本地地址与 MAC 不符 | 警告 |
| 9 | 设备画布坐标完全相同（叠在一起看不见） | 警告 |

### 规则是怎么定的（不是猜的）

对着 PT 9.0.1 自带的 **293 个原生示例文件**反推：
每个规则都必须对 PT 自己写的文件成立，否则就是误报。

校准过程：

1. 初版规则对 40 个原生文件报 39 个错 → 全是误报
2. 逐条查原因，修掉 5 类误报：
   - 物理视图 NODE 是**嵌套**的，非贪婪正则只切到最外层 → 改成递归
   - `<CHILDREN>` 也是嵌套的，要数深度配对 → 不能用非贪婪
   - 链路的 `<FROM>`/`<TO>` 有**两种**形态：`save-ref-id:数字`（新式）和纯数字（旧式，设备序号）→ 两种都认
   - 有些原生文件**没有物理视图段**，或该段是空的 → 那种文件不要求设备注册
   - IPv6 场景里 PT 会把接口标识符改成指定值（`FE80::1`）→ 降为警告
3. 定稿后：**293 个原生文件全量校准，零误报**

同时对「已知有病」的文件做反向测试：缺前缀、id 重复、地址重复、uuid 对不上，
四类都必须被抓出来（`tools/test_pkt.py`）。

### 效果

```
$ python tools/verify_pkt.py out/UC-83.pkt
  · UC-83.pkt：21 台设备，0 个错误，0 个警告
```

修复前的旧文件：

```
  [错误] 9 个 SAVE_REF_ID 缺少 'save-ref-id:' 前缀，PT 认不出这是设备 id
  [错误] MEM_ADDR 重复（PT 按设备地址建索引，撞了就拒绝加载）：{...: 3, ...: 6}
  [错误] DEV_ADDR 重复（PT 按设备地址建索引，撞了就拒绝加载）：{...: 3, ...: 6}
```

**旧文件 16 个错误 → 新文件 0 个错误**，与人工排查的结论完全对上。

## 五、顺带修的：拓扑图布局

21 台设备原来挤成两排、标签互相压字（SW0/SW2 重叠、PC0/PC1 重叠）。
重写了 `pktlab/layout.py`：

- **按层次分行**：优先用 DSL 里的 `layer` 字段（层次本来就是设计决策，不该靠猜），
  没有则按「离终端的跳数」BFS
  → UC-83 排出 ISP → 边界 → 核心 → 汇聚 → 接入 → 终端 六层
- **同层均分**，列距随设备数自适应
- **宽层按 VLAN 边界拆行**（同一 VLAN 的设备尽量不跨行）
- 画布尺寸按内容自适应；VLAN 分组框按行独立画，标签移到框外左上角

## 六、回归：一次「越修越坏」的教训

上一轮的修复里，我顺手加了两个**没人要求**的改动：

1. 删设备时，连带删掉物理视图（机架图）里对应的 NODE
2. 设备改名时，同步改物理视图里那个 NODE 的 NAME

第 2 个只是让机架图显示的名字更准确；第 1 个是想让机架图「干净」一点
（删掉的设备不留残影）。**两个都不是加载所必需的**——而第 1 个把文件写废了。

### 怎么废的

物理视图的 NODE 是**嵌套**的（Intercity → Home City → … → Rack → 各设备）。
删节点时用了非贪婪正则 `<NODE>.*?</NODE>` 去切块：

```
<NODE>              <- Rack
 <CHILDREN>
  <NODE> PDU </NODE>       <- 非贪婪到这里就停了
  <NODE> Router0 </NODE>
 ...
```

切出来的「块」其实是「Rack 的开头 + PDU 一整块」。把它删掉，
连 Rack 的 `<CHILDREN>` 开始标签一起没了，留下一个孤儿的 `</CHILDREN>`
→ XML 结构损坏 → PT 报 **「Unable to open file. The file was not saved correctly.」**

只有当被删的设备正好是**某个容器的首个子节点**时才触发
（删 Router0 没事，删 PDU 就炸），所以本地跑生成器完全不报错。

### 为什么没被拦住

那版校验器全是正则检查，**压根没验 XML 是否合法**，所以十几个文件全绿通过。

### 修法

1. **回退**这两个改动，回到「已验证能打开」的行为：
   - 物理视图留着已删设备的残留节点 —— PT 完全容忍（实测：带残留节点的旧文件
     能打开、能 ping 通），不值得为「好看」冒风险
2. 校验器补上**第 0 条规则：XML 良构性**，排在所有检查之前
   （结构都坏了，后面查什么都没意义）
3. 自测补一条**回归测试**：删掉一半设备后，XML 必须仍然合法、写盘读回必须一致
4. 辅助函数 `_iter_nodes` / `_innermost_node` 按**深度配对**切 NODE 块，
   不用非贪婪；校验器改为复用同一份实现，避免两套逻辑漂移

### 验证「回退到位」

把现在生成的文件和 git 里**你实测过能打开的那版**（`a8d183f`）做结构对比：

```
UC-82  标签序列相似度 1.000000
       结构差异块 0 个  → 结构完全一致
       文本差异只有 X / Y 两类（布局改动带来的坐标变化）
```

扩容种子（`base_campus.pkt`）相对原种子也做了同样验证：

```
原种子 44373 个标签 → 扩容后 53206 个
差异操作：{'insert': 3}，非「纯插入」的操作：无
```

**只增不改**——结构上是已验证种子的严格超集。
