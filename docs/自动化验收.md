# 自动化验收（C2）

## 0 一句话结论

`run-accept.cmd` 双击即可，对全部用例算出「谁该通、谁该不通」，并检查配置是否自相矛盾，
输出 `out/<用例>_验收报告.md`。

**但要说清楚：这不是「在 Packet Tracer 里自动跑了一遍 ping」。**
PT 没有可脚本化的仿真接口（没有 CLI、没有 Python API 能触发 ping 或读回显），
所以验收器做的是**建模推算 + 配置一致性检查**，产出可核对的预期值，
再由人到 PT 里抽查。报告里也写了这句话，没有包装成「自动跑通」。

---

## 1 为什么不能真跑

| 想做的事 | 可行性 | 原因 |
|---|---|---|
| 命令行启动 PT 加载 pkt | ✗ | PT 无命令行参数接口 |
| 程序化敲 `ping` | ✗ | 无对外 API，仿真引擎闭源 |
| 读回 `show ip route` 文本 | ✗ | 同上 |
| 解析 .pkt 里的配置 | ✓ | 容器格式已完全逆向（`codec.py`） |
| 从配置推算连通性 | ✓ | 路由表 + ACL 语义是确定性的 |

所以「自动验收」的真实含义是：**把人工在 PT 里逐条 ping 的工作，换成从配置推算一遍，
人只需要抽检。** 这比不做好，但不能吹成 PT 自动化。

---

## 2 推算依据

全部来自已生成的配置，不是拍脑袋：

1. **同网段** → 二层直通（VLAN 场景要求同 VLAN，见第 3 节）
2. **跨网段** → 在路由器互联图上找路径
   - 每台路由器都必须有到目的网段的路由：
     - 直连接口，或
     - 全网跑同一种 IGP（rip / ospf / bgp）且路由器图连通（认为已收敛），或
     - 静态路由 / 默认路由匹配
   - 任何一跳缺路由 → 判不通，并指出是哪台路由器
3. **ACL** → 沿路径逐个接口检查入/出方向
   - 按规则顺序匹配，**第一条命中即生效**
   - 带 `port` 的规则不匹配 ICMP
   - 一条都不命中 → 末尾隐含 `deny any`
4. **网关** → 主机网关必须精确等于某台路由器的某个接口地址，否则判不通

---

## 3 六类一致性检查

| # | 检查 | 抓什么问题 |
|---|---|---|
| 1 | 主机网关有效性 | 网关写错网段 / 指向不存在的地址 |
| 2 | 点对点链路两端同网段 | 串口两端掩码不一致，链路起不来 |
| 3 | 业务网段有三层接口 | 网段划了但没挂到任何路由器，永远不可达 |
| 4 | ACL 有 permit 兜底 | 只写 deny 不写放行，隐含 deny 会误伤 |
| 5 | IGP 覆盖连通图 | 跑了 OSPF 但路由器图不连通，收敛不了 |
| 6 | 二层配套（VLAN 用例） | access 口划错 VLAN / 没 trunk 上联 / 路由器缺子接口 |

第 6 项是单独立出来的。UC-05 早期就是「access 口对了、trunk 对了、子接口也在，
但三者没对上」导致 ping 全丢，而这一层**三层模型完全看不到**——
连接通性矩阵都会显示全通。所以必须单独查一遍。

---

## 4 断言：让验收有判定

用例里可以声明预期，验收器据此给通过/失败：

```yaml
expect:
  reach:                 # 这些主机对应该能 ping 通
    - [PC0, SRV0]
    - [PC1, PC0]
  block:                 # 这些应该不通
    - [PC0, PC1]
```

判定规则：
- 有 `expect` → 以断言为准（推算结果 ≠ 预期 就 FAIL）
- 无 `expect` → 只看一致性检查
- 断言里写了不存在的设备名 → 标「未推算」，算失败（防止拼写错误静默通过）

方向是有意义的：UC-07 的 ACL 只挂在 R1 研发侧入方向，
所以 `PC0→PC1` 不通但 `PC1→PC0` 通，这两个都写进断言了。

## 5 反向测试：证明它不是摆设

一个永远通过的检查器没有价值。`tools/test_accept.py` 故意造 9 种故障，
逐条确认能被抓到，且报错信息说得清「哪台设备、哪个口、哪个 VLAN」。

```cmd
python tools\test_accept.py
```

| # | 注入的故障 | 期望被指出 |
|---|---|---|
| 1 | 好拓扑 | 断言 + 检查全过 |
| 2 | PC3 的交换机口划成 VLAN 10（应为 20） | 第 6 类检查 |
| 3 | SW0 的 Fa0/24 不再是 trunk | 第 6 类检查 |
| 4 | R1 少了 VLAN 20 的子接口 | 第 6 类 + 跨 VLAN 判不通 |
| 5 | ACL 挂反方向（in → out） | 断言失败（PC0→PC1 变通） |
| 6 | ACL 去掉 permit 兜底 | 第 4 类 + PC0→SRV0 被隐含 deny |
| 7 | 主机网关写错 | 第 1 类 + 判不通 |
| 8 | 两台路由器都不跑路由协议 | 跨三跳判不通 |
| 9 | 断言写错设备名 | 标「未推算」并算失败 |

**22 项检查全部通过。**

其中第 5、6 条特别值得看：它们验证了 ACL 的**方向性**和**隐含 deny** 是真的被建模了，
而不是简单粗暴地「有 ACL 就判不通」。

## 7 traceroute 路径断言与路由表断言（C2 补齐）

C2 的判定语要三样：**ping 矩阵、traceroute 路径断言、`show ip route` 关键条目断言**。
前两样之前只有「通/不通」的矩阵，路径数据虽然算出来了但没输出；第三样完全没有。
现在每份 `{uid}_验收报告.md` 多出两张表。

### 7.1 traceroute 跳序怎么来的

PT 里 `tracert 目的IP` 打印的是**每台路由器接收该包的接口地址**，最后一行是目的主机。
所以跳序按这个规则拼：

```
第 1 跳  = 源主机的默认网关（就是第一台路由器的入口地址）
第 k 跳  = 路径上第 k 台路由器的入口地址（前一台路由器连过来的那个口在本台上的地址）
最后一跳 = 目的主机 IP
```

以 UC-01 为例（PC0 → R1 → R3 → PC1）：

| 预期 | 源 → 目的 | 跳数 | 期望跳序 | 说明 |
|---|---|---|---|---|
| ✅ | PC0 → PC1 | 3 | `192.168.16.62 → 10.0.0.38 → 192.168.16.138` | R1 的 Fa2/0 是网关；10.0.0.38 是 R3 的 Serial0/0；末跳是 PC1 |

在 PT 里对着敲 `tracert 192.168.16.138`，三行地址应当一模一样。

### 7.2 不通的路径也要给「断在第几跳」

这是路径断言比 ping 矩阵有价值的地方：**ping 只告诉你通不通，tracert 告诉你断在哪。**
两种断法在 PT 里的表现不同，验收器分开建模：

| 断因 | PT 里的表现 | 跳序处理 |
|---|---|---|
| ACL 拒绝 | 该跳之后 `*  *  *`（静默丢弃，不回 ICMP） | 截到被 ACL 拦下的那台路由器为止 |
| 中途没有路由 | 该跳回 `!H`（host unreachable） | 截到缺路由的那台路由器，说明里标 `!H` |
| 源主机没网关 | 第 1 跳就失败 | 跳序为空 |

UC-07 的实例（ACL 挂在 R1 面向 PC0 的口、方向 in，包在 R1 就被丢掉）：

| 预期 | 源 → 目的 | 跳数 | 期望跳序 | 说明 |
|---|---|---|---|---|
| ❌ 应不通 | PC0 → PC1 | 1 | `192.168.20.1` | 第 1 跳后 `*  *  *`（R1 上 ACL 静默丢弃） |

注意这里**只有 1 跳**。早期版本把 R2 的地址也列进去了 —— 那台路由器根本没收到包，
是错的。判定「包终止在哪台路由器」的逻辑现在落在 `Pair.stop_at` 字段上，
跳序按它截断（`tools/test_accept.py` 第 [11] 组测试就是防这个回归）。

### 7.3 路由表断言

每台路由器 × 每个「有主机的远端网段」一条，给出**预期在 `show ip route` 里看到的那一行**：

| 路由器 | 目的前缀 | 类型 | 期望条目 |
|---|---|---|---|
| R1 | 192.168.16.0/26 | 直连 | `C    192.168.16.0/26 is directly connected, FastEthernet2/0` |
| R1 | 192.168.16.128/26 | RIP | `R    192.168.16.128/26 [120/1] via 10.0.0.38, 00:00:12, Serial1/0` |
| R3 | 192.168.16.0/26 | RIP | `R    192.168.16.0/26 [120/1] via 10.0.0.37, 00:00:12, Serial0/0` |

口径（报告里也写了）：

- `[AD/度量]` 中 **AD 是协议默认值**（直连 0 / 静态 1 / eBGP 20 / OSPF 110 / RIP 120）；
- **RIP 的度量是跳数，可精确推算**；
- **OSPF 的度量按接口带宽算**（`10^8 ÷ 带宽`，<1 记 1、>1 舍小数：以太 100Mb → 1、串口 1.544Mb → 64），
  这个值不只在路由表里显示，**还参与选路**（`_path_cost()` 加权最短路），所以「OSPF 会绕行」这种结论是从建模算出来的，不是写死的；
  但 PT 里串口默认带宽要看设备型号，实际以 `show ip ospf interface` 为准，数值可能有 1~2 的差；
- 静态路由的 AD 取 DSL 里写的 `admin_distance`（浮动静态会体现为 10）；
- `00:00:12` 只是占位的时间戳，PT 里显示的是设备运行时长，数值必然不同 —— **别拿它当断言**；
- **RIP 汇总后的重复行会合并**：同一主网络下的 `/25` 与 `/26` 在邻居路由表里都显示成
  `192.168.16.0/24`，PT 只出一行，所以断言表也只出一行，`说明` 列注明是哪两个子网并进来的
  （`accept._merge_summarized()`）。

推算不成立时（路由器图不连通、缺路由协议），这一行会标 `⚠️` 并说明原因，
例如「路由器图不连通或缺路由协议，R1 可能学不到 192.168.16.128/26」。
`tools/test_accept.py` 第 [14] 组就是把 R1 的路由协议删掉，验证它会标出来。

### 7.5 等价多路径（ECMP）断言

C2 只要求 ping 矩阵 + traceroute + `show ip route` 三样，ECMP 属于加分项
（实验 4-11 第 10 步、附录 UC-02 都要求「观察等价负载均衡」）。

做法：对每台跑 OSPF 的路由器、每个**至少两台路由器接入**的传输网段，
枚举各接入方向的最小代价路径，代价相同就记一条 `Ecmp`。报告里单独一节，
形如：

```
| R2 | 30.0.0.0/30 | 65 | `10.0.0.1` / `FastEthernet2/0` ／ `20.0.0.1` / `FastEthernet3/0` |
```

三条口径要写清楚：

1. **代价包含目的侧接口**：Cisco 的 OSPF 代价一直算到「目的网段所接的那个接口」。
   所以 R0 去 `192.168.16.128/26` 是 `[110/3]`（两段以太 + R1 面向 /26 的口），
   而 R2 去 `30.0.0.0/30` 的两条都是 `[110/65]`（一段以太 1 + 一端串口 64）。
2. **只给「可能交替」的判据，不说已经交替**：代价相等 ⇒ PT 会并列两个下一跳；
   数据面是否真轮流发属于 Simulation 行为，报告里写的是操作步骤，不是结论。
3. **不做 ECMP 的负载分配推算**：`traceroute` 期望仍按单条最短路给，
   不会因为存在等价路径就输出两套跳序。

**实测对账（2026-10-22，UC-82）**：R2 的 `show ip route` 真的出现两行
`O 30.0.0.0/30 [110/65]`（`via 10.0.0.1, Fa2/0` 与 `via 20.0.0.1, Fa3/0`），
与推算的共同代价、下一跳、出口**逐项一致**。

## 9 已知边界（报告里要写）

1. **没建模收敛时间**。OSPF 邻居从 down 到 full 要几十秒，验收器假设已收敛。
   刚打开 pkt 就 ping 会失败，这是正常的，不是配置错。
   **实测补充**：PT 的以太口还有 40 秒 DR 选举 `wait timer`，`show ip ospf interface brief`
   会显示 `State = WAIT`；同一份 pkt 前后两次 `tracert` 可能一个 3 跳、一个 4 跳（实测遇到）。
   判「不通」前先等满 60 秒。
2. **没建模 ARP / STP 阻塞**。生成环路的拓扑时，STP 会阻塞某些口，验收器按全通算。
3. **没建模 NAT、ACL 的时间段（time-range）、策略路由**。这三样当前 DSL 也不支持。
4. **只看 IPv4 ICMP**。UDP/TCP 的 ACL 规则不参与判定（带 port 的规则被跳过）。
5. **二层只有 VLAN，没有 trunk 的 allowed list 细化**。trunk 默认放行所有 VLAN。
6. **RIP 有类汇总：已完整建模到「能不能通」这一层**（这一条原先是边界，现在补上了）。
   - `_classful_cidr()` 把任意前缀折成主网络：`192.168.16.128/26 → 192.168.16.0/24`、`10.0.0.0/30 → 10.0.0.0/8`
   - `_rip_summarizes()` 判定是否在汇总：`protocol == "rip"` 且**不是**（`version == 2 and auto_summary is False`）
   - `_rip_summary_blocks(topo, router, dst_net)` 实现手册 4-10 的核心现象：路由器**直连主网络 M** 时，
     会丢弃从其他主网接口学来的 M 的子网路由——因为 v1 通告不带掩码，收到的主网络与本机直连主网络相同，视为重复
   - 判定插在「IGP 捷径」**之前**：先判直连面、再判有类汇总阻断、最后才走「全网跑 IGP 且图连通就算通」
   - 不通原因会区分两种说法，报告里能看出来是「协议固有行为」还是「配置漏了」
   - 路由表断言同步给出「学不到」条目（预期协议写 `R`、实际写 `（无）`），不是简单跳过
7. **OSPF 按代价选路：已建模**。`_iface_cost()` = 100Mb/s ÷ 带宽，<1 记 1、>1 舍小数
   （以太 100Mb → 1、串口 1.544Mb → 64，与手册一致）；`_path_cost()` 用 Dijkstra 加权，
   代价相同比跳数、再比路径字符串以保证确定性。起点跑 OSPF 时走加权最短路，否则走 BFS 最少跳。
   这条建模让 4-10 / 4-11 出现**同一拓扑下 RIP 与 OSPF 选路不同**的真实对照：
   RIP 走 1 跳串口、OSPF 走 2 跳以太绕行（代价 2 < 64）。
   仍未建模的是**等价负载均衡**（等代价多路径分摊）——见下一节缺口。
8. **等价负载均衡：已建模**（`_ecmp_asserts()`）。对每台跑 OSPF 的路由器、每个「≥2 台路由器接入」
   的传输网段，枚举各接入方向的最小代价路径，代价相同即产出 `Ecmp` 条目，
   报告里单列一节「等价多路径（ECMP）断言」，给出共同代价与各分支的下一跳/出口。
   - 4-11 里只有 R2 → `30.0.0.0/30` 成立：经 R0（1+64）与经 R1（1+64）都是 **65**；
   - 附录 UC-02 的三角串口拓扑也是真 ECMP（三条，代价 128），一并算了出来；
   - **仍然没建模**的是数据面的「轮流发」本身——ECMP 只保证「代价相同、有多条候选」，
     是否真的交替要在 PT 的 Simulation 里看事件列表，报告里写的是「怎么验」而不是「已验证」。
9. **不建模浮动静态的 AD 选路**。一台路由器上只认一个 `default_route`，
   「同前缀两条静态路由按 AD 取最优」没有实现——这也是 UC-08 没做的原因（见
   `docs/评分对照_差距分析.md` 第 9 节）。
10. **不校验 pkt 里的端口地址**（验收器读的是 DSL，不读 pkt 容器）。
    这一条踩过真坑：设备从骨架克隆，端口节点里带着骨架自带的旧 IP，
    与配置里另一个接口的地址撞车时，PT 会拒绝后者，现象是「`show run` 有地址、
    接口却不生效、也不进 OSPF」。生成端已用 `Device.clear_port_ips()` 修掉
    （端口地址只由 running-config 提供），`test_cfgprofile` 第 [8] 组守住；
    但**验收器本身仍然看不出这类问题**，只能靠 PT 实测——这是又一条
    「静态推算 ≠ 跑过」的边界。

这些不是「没想到」，是主动划的范围——两周时间里，把主干场景做扎实比铺开做半成品值。
