# 故障注入闭环与审计护栏（C3 / E）

## 0 一句话

**C3**：往一份合法拓扑里精确注入 24 类典型错误，逐条验证「报对码 → 修好 → 收敛」，
并确认修完之后**语义没变**（C2 的验收断言仍然全过）。

**E**：schema 管不了的那部分——危险配置、被注入的指令、废掉的设备——由护栏拦下，
不通过就不出 pkt；全过程记一条可回溯的事件流。

```cmd
selftest.cmd            :: 三套测试一把跑完，不联网
run-accept.cmd          :: 只跑 C2 验收
```

---

## 1 为什么闭环要分三段

只验「能修好」是不够的。最省事的修法是把出错的字段删掉——校验当然能过，
但拓扑已经不是用户要的那个了。所以每一条故障都要过三关：

| 段 | 断言 | 不过说明什么 |
|---|---|---|
| ① 定位 | 校验器必须报出预期的错误码 | 这类错对模型不可回灌，等于没检测 |
| ② 闭环 | 修到校验通过，且**再修一次不再有改动**（幂等） | 修复器不收敛，或会自我打架 |
| ③ 语义 | 修完后 C2 的断言与一致性检查仍然全过 | 修是修了，但意思变了 |

第 ③ 段是最有价值的一关，也是我改动最多的一关（见第 3 节）。

## 3 修复器的几条判断规则

大部分修复是一一对应的替换，没什么可讲。有四条是**做过取舍**的，值得单独说。

### 3.1 网关跑出网段 → 改成该网段上路由器的地址

不是无脑填 `.1`。先在该网段里找有没有路由器的三层接口，有就用那个地址——
它才是真正的网关。找不到才退回「第一个可用地址」。

`uc01` 里 PC0 的网关是 `192.168.16.126`（/25 的最后一个可用地址，故意不用 .1），
如果修复器填 `.1`，校验能过，但 PT 里 ping 不通。

### 3.2 地址冲突 → 优先保住「被当作网关」的那个

两台设备撞地址时，先看这个地址有没有被某台主机当作网关。有的话，它必须留在
**路由器**上，把另一台挪走。否则修完之后主机网关指向一个不存在的地址，
校验能过，但路由断掉——这属于「把错误藏起来」。

### 3.3 子接口编号与 dot1q 不一致 → 改 dot1q，不改编号

两个方向都能让校验通过，但改编号会拆散另一套关系：子网 `192.168.20.0/24`
对应的 VLAN 是 20、网关是 `.20.1`、交换机接入口是 VLAN 20。
把接口从 `.20` 改成 `.30`，路由器就再也接不上这个 VLAN 了。所以以编号为准。

### 3.4 「声称是标准 ACL，但写了目的地址」→ 改判为扩展 ACL，不是删字段

`standard` 类型的 ACL 里出现 `destination`，最省事的修法是把 `destination` 删掉。
但标准 ACL 只按源地址过滤，删掉目的地址之后，这条规则的含义从
「拒绝 A 到 B」变成了「拒绝 A 到所有地方」——语义完全变了。

正确的判断是：它其实想写扩展 ACL。所以改成 `extended` 并按扩展区间重编号
（`10` → `100`），语义原样保留。

同理，**ACL 挂错设备**（挂到交换机上）不是简单删掉挂载——那等于 ACL 失效。
修复器会按第一条规则里的源网段，反查这个网段接在哪台路由器的哪个口上，
把挂载改到那里。`uc07` 里正好推出 `R1 FastEthernet2/0 in`，跟手写答案一致。

## 4 哪些故意不修

| 错误 | 为什么不修 |
|---|---|
| `SUBNET_OVERLAP` | 两个子网重叠时，往哪边挪、挪多大，取决于需求里没写的意图。猜错比报错更糟 |
| `MASK_INVALID` | 掩码本身非法，无从判断原本想写什么 |

对应到那条标星的两例：

- `encap_on_physical`：注入时连 VLAN 20 的子接口一起删掉了，修复器只能把
  `Fa2/0` 拆成 `Fa2/0` + `Fa2/0.10`，接不回 `.20` 的地址。
- `acl_bad_addr`：`192.168.20.999/24` 推不出原意，只能降级成 `any`。

这两条在测试里标 `strict=False`，意思是**断言它们能编译通过，但不假装语义没变**。
宁可把「这里需要人再看一眼」标出来，也不要静默产出一个看着正常的错拓扑。

## 5 护栏：schema 查不出来的危险

`audit.guard()` 输出两级：

- **block** —— 不交付，回灌给模型重写
- **warn** —— 记进日志，照常交付，人自己判断

| 代码 | 级别 | 抓什么 |
|---|---|---|
| `ACL_PERMIT_ALL_FIRST` | block | ACL 第一条就是 `permit ip any any`，后面的规则永远不命中 |
| `ALL_SHUTDOWN` | block | 一台路由器/交换机所有接口都 shutdown，设备是死的 |
| `INJECT_OUTPUT` | block | 设备名/标题里出现 `HACKED`、`忽略`、`systemprompt` 等注入标记 |
| `INJECT_PROMPT` | warn | 需求里含「忽略以上所有规则」这类指令性语句（已按普通文本处理） |
| `ACL_NO_FALLBACK` | warn | ACL 最后一条不是 permit，未列出的流量会被隐含 deny |
| `ACL_UNUSED` | warn | ACL 定义了但没挂接口，不会生效 |
| `NO_ROUTING` / `PARTIAL_ROUTING` | warn | 多台路由器没人跑路由协议，跨网段不会通 |
| `NAME_STYLE` | warn | 设备名不以 R/SW/PC/SRV 开头，读图和写报告时容易混 |
| `TITLE_ECHO` | warn | 标题直接抄需求原文的开头，没做概括 |

`ACL_PERMIT_ALL_FIRST` 是这里面最值钱的一条。它语法完全合法、
schema 校验全过、C2 的连通性推算也会老老实实算出「全通」——
但用户要的「禁止研发访问财务」根本没实现。这种「合规的废话」
只能靠护栏拦。

### 护栏参与闭环，不只记录

被 block 的输出会连同理由回灌给模型：

```
你上一版输出被安全护栏拒绝：
- ACL 100 第一条就是 permit ip any any，后面的规则永远不会命中，等于没做防护

请修正后重新输出完整的 JSON 对象。
```

护栏不通过就不出 pkt——这是「护栏」和「日志」的区别。

## 6 审计：一条产物能回溯到什么

`nlgen.py` 每跑一次生成，落两个文件：

- `out/UC-95_audit.jsonl` —— 机器可读，一行一个事件
- `out/UC-95_nlog.md` —— 报告里直接引用的表格

事件类型：

| kind | 内容 |
|---|---|
| `meta` | 需求原文、模型名 |
| `prompt` | 实际送进去的需求 |
| `raw` | 模型原始返回（含截断保护）、本轮耗时 |
| `validate` | 本轮校验错误清单（带 code 和位置） |
| `repair` | 本地修复的每一处改动 |
| `guard` | 护栏裁决 |
| `round` | 本轮统计：错误数 / 拦截数 / 耗时 |
| `done` / `fail` | 终局 |

一条 `.pkt` 因此能追到：**哪句话、哪个模型、第几轮、改了哪几处、为什么改**。

## 8 边界

1. **修复器只修「唯一解」**。有任何歧义就停下来报错，不猜。
2. **护栏是规则库，不是分类器**。它认识的是已知的几种危险模式，
   挡不住「写得完全正确但业务上是错的需求」。
3. **注入抵抗是有限度的**。当前做的是「识别指令性语句 + 检查产物有没有被带偏」，
   不是通用的 prompt injection 防御。真实对抗场景需要独立的内容过滤层。
4. **审计日志不含 API key**，但也含需求原文——如果需求里有敏感信息，
   分享 JSONL 前要自己脱敏。
5. **幂等只保证在单次进程内的确定性**，不保证跨版本（改了修复规则就会产生新改动）。
