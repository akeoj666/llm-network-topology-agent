# D2 失败案例分析：LLM 犯过的错、根因与工程对策

> 评分表 D2 要求：**≥2 个 LLM 犯错实例**，分析根因（prompt 歧义 / 知识错误 / 格式漂移）并给出工程对策。
> 本文给 **5 个真实案例（全部来自本项目 2026-10-20 ~ 10-21 的实际调试过程）+ 1 个工具自身缺陷**。
> 每个案例都标了证据文件，可对着仓库复核 —— **不编造、不美化**。

---

## 0 口径说明（先说清楚，避免被当成编故事）

| 分类 | 含义 | 本文数量 |
|---|---|---|
| **真实犯错** | 模型输出的东西在 PT 里实跑失败，或产物被错误覆盖，有用户截图/日志为证 | 4 |
| **设计期预判** | 已知这类错高发，用**故障注入**复现并验证修复器，但没有等到模型自然犯 | 1 |
| **工具缺陷** | 不是模型错，是我们的校验器/生成器漏了 | 1 |

之所以要把这三类分开写：评分表红线第 4 条是「日志或报告造假」。
**拿着注入测试冒充「模型真实犯错」是最容易被追问倒的地方**，所以第 5 个案例明确标注为注入复现。

## 2 案例 1：不存在的接口名，让整段配置变成废纸

### 现象
第一版用「克隆现成 pkt 骨架 + 注入配置」的方式生成 `gate2_config.pkt`。
用户在 PT 8.2 里打开，`R1-EDGE` 上 `show run` 报 `% Invalid input detected at '^' marker.`，
`Serial0/0` 没有 IP，`Fa2/0` 是 `administratively down`。

### 根因（知识错误）
模型（和当时的我）都按 2811 的习惯写 `interface FastEthernet0/0`。
但 **PT 的 `Router-PT-Empty` 装了 `PT-ROUTER-NM-1S` 模块后，局域网口是 `FastEthernet2/0` 和 `FastEthernet3/0`，根本没有 `Fa0/0`**。

更狠的一点是 PT 的回放机制：

> **PT 从第一行开始逐行执行配置，遇到第一行非法命令就中止后面全部。**
> 所以错一个接口名，不是「这一行无效」，而是**整段配置报废**。

这也是为什么「配置看起来写得很像那么回事」在 PT 里完全没有意义 —— 它只认第一行是否合法。

### 工程对策
1. **硬件端口目录写死进代码**，装配时二次校验，不允许出现目录外的端口：

   ```python
   # pktlab/config.py
   CATALOG = {
       "Router-PT-Empty": {"serial": ["Serial0/0", "Serial1/0"],
                           "lan": ["FastEthernet2/0", "FastEthernet3/0"]},
       "2911":            {"serial": [], "lan": ["GigabitEthernet0/0", ...]},
       "2960-24TT":       {"lan": [Fa0/1 … Fa0/24, Gi0/1, Gi0/2]},
       "PC-PT":           {"lan": ["FastEthernet0"]},
   }
   ```

2. 提示词里把这张表作为**硬约束**写进去（不是「建议」）。
3. `LINK_REF` / `iface` 校验码：链路引用了设备不存在的端口 → 直接 BLOCK，不给交付。

### 回归
`examples/uc01~uc07`、`UC-91~95` 全部生成的配置里，接口名只出现 `Serial0/0`、`Serial1/0`、
`FastEthernet2/0`、`FastEthernet3/0`、`FastEthernet0/1..24`。
用户实测 gate4/gate5 两个文件在 PT 里**配置真实生效**（`Serial0/0 = 10.0.0.29`、`Fa2/0 = 192.168.16.1`）。

### 顺带纠正的一个误判
第一次看到 `show run` 报 invalid，我误以为是「配置没注入进去」。
实际是**用户模式 `>` 下不能敲 `show running-config`**，要先 `enable`。
这个误判写进了 `docs/验证清单` 和粘贴指南 —— 调试时先排除「操作姿势错」，再怀疑「数据错」。

## 3 案例 2：模型对编号不敏感，第二次产物覆盖第一次

### 现象
用真实 key 连续跑两句不同需求，产物目录里只剩一套文件。
查 `out/*.yaml` 发现两次生成的 `meta.id` **都是 `UC-91`**，而 `nlgen.py` 直接拿模型的 id 当文件名 —— 第二次把第一次的
`pkt / yaml / png / configs / nlog` 全部覆盖，**第一次的成果直接没了**。

### 根因（格式漂移）
模型对 `id` 这种「无业务含义的标识」极不稳定：few-shot 示例里出现过 `UC-91`，它就倾向于复用。
校验器当时只校验「字段是否合法」，不校验「这个 id 是不是已经被占用了」——
因为单看一份输出，`UC-91` 完全合法。

这类错最阴的地方：**它不是 legality 问题，是 liveness 问题**。

### 工程对策
不给模型决定权，编号由本地分配：

```python
def next_id(out: Path) -> str:
    used = {int(m.group(1)) for p in out.glob("UC-*.yaml")
            if (m := re.fullmatch(r"UC-(\d+)\.yaml", p.name))}
    return f"UC-{max(used | {90}) + 1:02d}"
```

- `nl.translate(..., id_hint=uid)` 在**解析后强制覆盖**模型返回的 id（不是只在提示词里要求）
- 新增 `--id` 允许人工指定
- 打印「自动分配 UC-xx」，让用户知道产物落在哪

### 回归
修完之后跑 UC-93/94/95，模型返回的 id 依然是错的（`UC-92`），但**落盘全部正确**
—— 说明这条对策真正闭环在代码层，不依赖模型听话。

> 救回数据：用会话里读到的原文重建 YAML，`gen.py` 重新生成，保住了 UC-91（双路由 OSPF）和 UC-92（三路由 RIP VLSM），没多花 API 调用。

## 4 案例 3：VLAN「配了但不存在」——配置行生效 ≠ 设备状态生效

### 现象
UC-05（单臂路由）在 PT 里打开：

- `show vlan brief` 只有 VLAN 1 + 1002–1005，**没有 VLAN 10/20**
- 但 `Fa0/1–Fa0/6`、`Fa0/24` **已从 VLAN 1 的端口列表消失** → `switchport access vlan 10` 是生效的
- 结果：同 VLAN 内 ping 不通，跨 VLAN 更不通

「一半生效一半不生效」，比全错更难查。

### 根因（系统认知错误）
真实 IOS 的 **VLAN 数据库不在 `running-config` 里**，在 `flash:vlan.dat`。
`show running-config` 本来就不显示 `vlan 10`；PT 的配置回放**不认这几行**（不报错、也不生效）。
`show vlan brief` 读的是设备 XML 里的 `<VLANS>` 节点。

于是：**端口成员关系来自 RUNNINGCONFIG（生效了），VLAN 本身来自 XML 的 VLAN 库（没生效）**。

而且 XML 里有**两份** VLAN 库，都要写：

| 位置 | 路径 |
|---|---|
| 运行态 | `<SCP_SERVER_ENABLED>` 之后的 `<VLANS>` |
| flash 文件 | `<FILE_MANAGER>` → `flash:` → `<FILE class="CFile">` `<NAME>vlan.dat</NAME>` → `<FILE_CONTENT class="CVlanDatFileContent">` |

### 工程对策
`Pkt.set_vlans()` 直接改 XML，并且：

- 用 `<VLANS>` 里的 `default` 条目当模板，**保留属性顺序**（PT 对属性顺序敏感，重排序会导致打不开）
- 保留系统 VLAN 1、1002–1005，业务 VLAN 插在中间
- **递归处理设备块内所有 `<VLANS>`**（运行态 + vlan.dat），同步修正 `<VLAN_COUNT>`
- 种子里没有 `vlan.dat` 时自己补一份（插 `<FILE class="CFile">` 到 flash 的 `<FILES>` 末尾，并维护 `FILE_COUNTER`）

### 回归
`assemble.build` 对每台 `role == switch` 都调一次 `set_vlans`；
UC-05 产物里 `show vlan brief` 该有的 VLAN 10/20 都在，`encapsulation dot1Q 10/20` 与 VLAN 一致。

### 推广成的规则（写进设计文档）
> PT 的状态有两条来源：**RUNNINGCONFIG（接口级）+ 独立的运行时状态节点（VLAN 库、路由表等）**。
> 只改 RUNNINGCONFIG 时，凡是有独立状态容器的功能，都要回头检查一遍 XML。

这条规则后来直接催生了案例 4。

## 5 案例 4：网关「命令行是对的，界面里是空的」

### 现象
gate2 里 `PC-A` 的 IP 已改成 `192.168.16.10`，但 **Default Gateway 仍显示 `192.168.1.1`**（旧值）。
命令行/配置看着都对，图形界面不对 —— 而用户就是看图形界面判断「配没配上」。

### 根因（知识错误 + 字段冗余）
PC 的网关在 `.pkt` 里**存两份**：

| 位置 | 谁在读 |
|---|---|
| `<MODULE>/<SLOT>/<MODULE>/<PORT>/<PORT_GATEWAY>` | 配置回放 / 内部模型 |
| `<ENGINE>/<GATEWAY>`（在 `SYS_NAME` 之后） | **Desktop → IP Configuration 窗口** |

只改端口级：IP 会变、网关不变。这也解释了为什么「我的配置明明写了 `ip default-gateway`」没用 ——
主机根本不走命令行那条路。

### 工程对策
`Device.set_host_ip()` 两处同改：

```python
_GW_RE     = re.compile(r"<PORT_GATEWAY>([^<]*)</PORT_GATEWAY>")
_SYS_GW_RE = re.compile(r"<GATEWAY>([^<]*)</GATEWAY>")

block = _GW_RE.sub(..., block, count=1)   # 端口级
block = _SYS_GW_RE.sub(..., block)        # 设备级（全部）
```

`tools/gate_build.py` 增加「网关双字段打印」，每次生成都自查一遍。

### 回归
gate2 重新生成后，PC IP Configuration 窗口里网关与清单一致；
后续 UC-01（网关取子网最后一个可用地址 `.62 / .190`）在 PT 里 ping 通。

## 6 案例 5：标准 ACL 里写了 `destination`（注入复现，**非模型自然犯错**）

> 明确标注：这一条是**用故障注入构造的**，用于验证修复器，不是等模型自己犯的。
> 之所以列出来，是因为它是「prompt 歧义」这类根因最典型的代表。

### 现象
需求只写「禁止研发部访问财务部」。模型选择了 ACL `10`（标准 ACL 的编号范围）却写了带目的地址的规则：

```
access-list 10 deny ip 192.168.20.0 0.0.0.255 192.168.10.0 0.0.0.255
```

### 根因（prompt 歧义）
「禁止 A 访问 B」只描述了**意图**，没说**用哪种 ACL**：

- 标准 ACL（1–99）只能按**源**过滤
- 扩展 ACL（100–199）才能按源 + 目的 + 协议

模型挑编号时凭「第一个 ACL」的直觉给了 `10`，写规则时凭意图给了 `destination`。
**两条单独看都合理，合起来在 PT 里是语法错误** —— 标准 ACL 不接受第二个地址。

### 工程对策（两道）
1. **提示词写死编号规则**：「1–99 只能按源；要按目的必须用 100–199」。
2. **修复器不删字段，改判类型**：

   ```python
   # pktlab/repair.py  _fix_acl()
   Fix("ACL_STANDARD_SHAPE", label,
       "规则里有目的地址/端口，实质是扩展 ACL，改判为 extended")
   # ACL 10 → ACL 100，规则原样保留
   ```

   为什么不删 `destination`：删了虽然语法合法，但**用户要的隔离就没了** —— 变成「禁止所有到任意地址」，
   语义跑偏比报错更危险。

### 回归
校验码 `ACL_STANDARD_SHAPE` 有反例注入测试（`tools/test_faults.py`），24 条故障里
22 条本地一次修完、2 条明确标为不可修（`encap_on_physical`、`acl_bad_addr`），不假装能修。

## 7 案例 6：校验器自己漏了最常见的错（工具缺陷）

### 现象
写故障注入测试时发现：「两台 PC 配了同一个 IP」这种**最典型**的错误，校验器一条都没报。

### 根因
`_check_addressing` 只遍历 `d["interfaces"]`（路由器/交换机的接口），
**完全没扫 `d["ip"]`**（主机的地址字段）。主机的地址根本不在 interfaces 里。

### 对策与反思
把 `<host>` 纳入冲突表后立刻能报 `DUP_IP`。

这条不是模型的错，但必须写进来：**「LLM 会犯错」这个前提成立时，如果裁判自己也是错的，闭环就是假的。**
所以本项目的故障注入测试是双向的 —— 既测模型输出，也测校验器能不能报出来（`test_accept.py` 22 项、
`test_faults.py` 24 条、`test_nl.py` 6 组）。

## 8 根因分布与「三道防线」

### 分布

| 根因类型 | 案例 | 占比 |
|---|---|---|
| **知识错误**（端口型号、字段双存） | 1、4 | 2 / 6 |
| **系统认知错误**（状态不在配置里） | 3 | 1 / 6 |
| **格式漂移**（编号重复） | 2 | 1 / 6 |
| **prompt 歧义**（ACL 类型） | 5 | 1 / 6 |
| 工具缺陷 | 6 | 1 / 6 |

一个观察：**这些错没有一个出在「模型不会写配置」上**。
模型写 `ip address`、`router rip`、`encapsulation dot1Q` 都写得对。
错全部落在**「PT 这个特定工具的隐性事实」**上 —— 端口型号、字段存哪、状态存哪、遇到非法行怎么处理。

所以本项目的工作重点不是「教模型写 IOS」，而是**把 PT 的隐性事实变成显性约束**。

### 三道防线（按拦截成本从低到高）

| 防线 | 手段 | 拦住了哪些 |
|---|---|---|
| ① 提示词 | 硬件端口表、ACL 编号规则、`no auto-summary` 等硬约束 + 2 个全覆盖 few-shot | 减少犯错概率，但**不可依赖**（案例 2 证明模型仍会无视） |
| ② 静态校验 + 本地修复 | 30+ 校验码（`DUP_IP` / `SUBNET_OVERLAP` / `ACL_STANDARD_SHAPE` …）+ 24 条确定性修复器 | 语法、编址、引用一致性；**22/24 一次修完，0 次 API 调用** |
| ③ 语义护栏 + 审计 | `ACL_PERMIT_ALL_FIRST` / `ALL_SHUTDOWN` / `INJECT_OUTPUT` 三个 block 级护栏；全事件落盘 JSONL | 「语法全对但防护等于零」这类**校验器抓不到**的问题 |

关键设计：**只有三道防线都过不了的错误才回灌给模型重写**，且回灌的是「修完还剩的」错误，不是原始全量。
实测 UC-91~95 全部第 1 轮通过（0 修复、0 拦截），说明防线没有把简单问题复杂化。

## 9 反向案例：模型有时候比我的参考实现更对

这一条很重要，因为它决定了**怎么评估「模型错了」**。

需求原文：「192.168.16.0/24 **前一半**给行政部，192.168.16.128/26 给研发部」

| | 行政部网段 |
|---|---|
| 模型输出 | `192.168.16.0/25`（.0–.127）—— **字面正确** |
| 我的 `examples/uc01.yaml` | 初版写成 `192.168.16.0/26`（.0–.63）—— **不符合「前一半」**；2026-10-22 复核已改为 `/25` |

其余（三条 /30、RIP v2 + `no auto-summary`、3R/2SW/2PC、PC↔SW 直通线）完全一致。
网关模型取 `.1`，我取子网最后一个可用地址（需求未规定，两种都合法）。

**结论：做「与人工参考对比」时，不能简单判模型错。**
参考实现本身也可能偏离需求原文，所以 D1 的「拓扑生成正确率」用的是第三条判据 ——
**需求逐字还原度 + 可运行性（PT 实跑 / 静态推算）**，而不是「像不像我手写的那份」。

## 10 可直接引用的 300 字摘要

> 本项目记录了 6 类失败，其中 4 个是 LLM 真实犯错（PT 实跑失败或被覆盖），1 个为 prompt 歧义引起的注入复现，1 个为校验器自身缺陷。
> 根因分布：知识错误 2、系统认知错误 1、格式漂移 1、prompt 歧义 1、工具缺陷 1。
> 显著特征是没有一个错出在「模型不会写 IOS 命令」上，全部落在 Packet Tracer 的隐性事实上——
> 端口型号（`Router-PT-Empty` 只有 `Fa2/0`、`Fa3/0`）、字段冗余（网关存两份，图形界面读设备级那份）、
> 状态分离（VLAN 库在 `flash:vlan.dat` 而不是 `running-config`）、错误传播（回放遇到首行非法命令即中止后续全部）。
> 对策按成本分三层：提示词硬约束（概率性）、静态校验 + 24 条确定性修复器（22 条本地一次修完、零 API 调用）、
> 语义护栏 + 全事件审计（拦住「语法全对但防护为零」）。三道防线都过不了才回灌模型重写。
> 同时记录了反向案例：模型在「/24 前一半」这一项上比人工参考实现更忠实原文，
> 故评估以「需求还原度 + 可运行性」为准，而非与参考实现的一致性。
